# feathercritty

feathercritty is the terminal emulation library used by [featherbit terminal](https://github.com/featherbitplatform/terminal): the VT parser handler, the grid with its scrollback, selection, search and the PTY event loop. It is a fork of `alacritty_terminal` 0.26.0 with a few small changes, listed below.

The crate is not published on crates.io. Use it as a git dependency pinned to a commit:

```toml
[dependencies]
feathercritty = { git = "https://github.com/featherbitplatform/feathercritty", rev = "<full commit sha>" }
```

## Origin

The repository holds the history of the `alacritty_terminal/` directory of [alacritty/alacritty](https://github.com/alacritty/alacritty), extracted with `git subtree split` (see [Updating from upstream](#updating-from-upstream)):

- `upstream` is the extracted history of upstream `master`, unchanged.
- `main` starts at the `alacritty_terminal_v0.26.0` release (tag `alacritty_terminal_v0.26.0` here, commit `a6b23e80c7fe4e416e96a39b34cb300fa9db3aca`; the release commit lives on upstream's `v0.17` branch, so it is not on `upstream`) and adds the changes below as separate commits.

## Why this fork exists

feathercritty is a fork of [`alacritty_terminal`](https://github.com/alacritty/alacritty/tree/master/alacritty_terminal), the terminal emulation library of the Alacritty project, maintained for [featherbit terminal](https://github.com/featherbitplatform/terminal).

featherbit terminal is developed with the help of AI coding tools. The Alacritty project does not accept contributions that include content generated by large language models ([CONTRIBUTING.md](https://github.com/alacritty/alacritty/blob/master/CONTRIBUTING.md)), and we respect that choice. Rather than send such changes upstream, we keep them here, so featherbit terminal can keep moving forward (for example on scrollback memory use) without asking the Alacritty maintainers to review or carry them.

This fork is not affiliated with or endorsed by the Alacritty project. Please do not report issues with this fork to Alacritty; open them here instead. All credit for the original work goes to the Alacritty authors.

## Changes from alacritty_terminal 0.26.0

Files changed by this fork start with the line `// Modified by the featherbit authors for feathercritty; see README.md for the list of changes.` (`#` in `Cargo.toml`).

### 1. Keyboard mode stack eviction (crash fix, upstream commit)

`src/term/mod.rs`, `Term::push_keyboard_mode`. When the kitty keyboard protocol's flag stack is full (`KEYBOARD_MODE_STACK_MAX_DEPTH`, 4096), 0.26.0 evicts the oldest entry from the wrong stack:

```rust
// before
let removed = self.title_stack.remove(0);
// after
let removed = self.keyboard_mode_stack.remove(0);
```

With an empty title stack the original line panics (`Vec::remove(0)` on an empty vector), so any program or remote host that sends `CSI > flags u` 4097 times crashes the terminal's parser while the protocol is enabled. This is upstream's own fix ("Fix Kitty keyboard mode stack size limit", made after 0.26.0), cherry-picked from `upstream` with its original authorship.

### 2. Scroll counter on the grid (scrollback search)

`src/grid/mod.rs`: `Grid` gains a `scrolled_lines: i64` field (skipped by serde), incremented by `positions` where `Grid::scroll_up` rotates the whole buffer into history, and a getter `Grid::scrolled_lines()`. `src/grid/resize.rs`: `grow_lines` subtracts the lines it adds (lines pulled back from history move down the screen, and the rotation its `scroll_up` counts only undoes the growth), so the counter can go below zero (wrapping arithmetic). `scrolled_lines() + line` is a line number that stays the same while output scrolls the line upward and while the screen grows or shrinks, which featherbit terminal's find bar uses to keep its matches and current match in place as new output arrives. Nothing in the library reads the field.

### 3. Inactive grid getter (tab export)

`src/term/mod.rs`: `Term::inactive_grid()` returns the grid that is not shown (the normal screen and its scrollback while the alternate screen is active). featherbit terminal's tab export writes the normal screen's history even while a full-screen program (vim, less, top) has the alternate screen up. Read-only; nothing else changes.

### 4. Packaging

- The package is named `feathercritty`; the doc test and `tests/ref.rs` use the new name. Authors and license are unchanged; `repository` and `homepage` point here, and `publish = false` keeps the crate off crates.io.
- Version scheme: `<alacritty_terminal version>+fbterm.<n>`, currently `0.26.0+fbterm.8` (changes 10 to 16). The build metadata (`+fbterm.n`) counts this fork's revisions on top of one upstream release and starts again at 1 when `main` moves to a new upstream release. Cargo ignores build metadata when comparing versions, which does not matter for a git dependency pinned by `rev`.
- The manifest no longer inherits `edition` and `rust-version` from the Alacritty workspace (both set to the workspace's values, 2024 and 1.85.0), and `readme` points to this file.
- `LICENSE-APACHE` is a copy of the upstream file instead of a symlink into the Alacritty workspace. The Alacritty workspace's `rustfmt.toml` (nightly options) and the `Cargo.lock` shipped with the published 0.26.0 crate are included so the crate formats and builds on its own.
- `src/lib.rs` allows `clippy::question_mark`: clippy releases newer than the upstream code flag three matches in `src/tty/unix.rs`, and the crate denies `clippy::all`. Allowing the lint keeps the upstream code unchanged.
- The reference test data in `tests/ref` (about 46 MB on disk) is kept. The whole repository history packs to about 1 MiB, so fetching it as a git dependency stays cheap.

### 5. Regex search over wrapped wide characters (hang fix)

`src/term/search.rs`: `Term::search_next`, `Term::next_match_right`, `Term::next_match_left`, `Term::regex_search_internal`, `RegexIter` (`new`, `next`, the cycle-check fields and `bound_fired`), `LazyDfa` (one field), and new items `Term::final_match`, `Term::last_in_range_before_repeat`, `Term::match_in_range`, `Term::glyph_cells`, `Term::glyph_end`, `Term::expand_wide_underflows`, `Term::search_distance`, `RegexSearch::take_bound_fired` and `LoopState`. `0.26.0+fbterm.2` to `+fbterm.4` fixed the hangs by changing how the iteration stops and cutting matches to the range; that changed answers 0.26.0 gives inside the range and produced "matches" whose text the pattern does not match. `0.26.0+fbterm.5` replaces it with the rules below.

**The trigger** is a leading spacer next to the end of a search. With a wrapped wide character after it (the wide character at column 0 of the next line, its spacer at column 1), searches step over the character two or three cells at a time: left from its spacer to the leading spacer, right from the leading spacer to its spacer. With a stale leading spacer, one whose next line does not start with a wide character (a resize or an erase leaves it behind, sometimes in the middle of a line), a rightward step still reads the next cell in its place and steps over the cell after it. 0.26.0 checks for its end only on the cells where a step lands, so:
- `regex_search_internal` can step over its end and read around the buffer; when the text gives it no match, forever. That hung leftward `search_next` with `max_lines` (its end is column 0 of any line), the empty pattern, and searches from a cell to itself;
- `RegexIter` stops only when a match ends exactly on its end. A match covering the end, or ending behind its origin next to a stale spacer, sends it back to an origin it already searched from, and it cycles through the same matches forever, so `search_next` never returns; this hung unbounded searches too, the find bar's ordinary case;
- matches can lie outside the searched range: the reading runs past the end, or a search from a cell to itself reads a full lap.

**The rules now:**
1. **The iteration is 0.26.0's.** `regex_search_internal`, `regex_search_left`/`right`, `RegexIter` and the choice in `search_next` (the first match past the origin, else the first match) run 0.26.0's code: same starts, stops, steps, second searches and continuation. `RegexIter` yields exactly 0.26.0's matches, out-of-range ones and repeats included.
2. **Bounds only where 0.26.0 would never end.** Both are exact cycle checks (Brent's algorithm, constant memory), so they fire only where 0.26.0 provably repeats itself forever, and nowhere else:
   - `regex_search_internal`: each time the search wraps around the buffer it records everything its further course depends on (`LoopState`: position, DFA state, bytes consumed so far up to 3, the match so far, the line-wrap flag, the DFA cache's clear count); when that repeats, so would every later lap. The search then returns no match.
   - `RegexIter`: each step depends only on its origin, so an origin it already searched from means it repeats forever. The iteration then ends.
   Either way `RegexIter::bound_fired` is set.
3. **Only the final answer of `search_next` changes, and only when 0.26.0 has none in range.** When the iteration hit a bound (0.26.0 never returns, or panics: rule 5), or 0.26.0's answer lies outside the searched range, `search_next` returns the last match inside the range that the iteration produced, or `None`. An iteration that 0.26.0 repeats forever counts up to its first repeated match (found with the second half of Brent's algorithm by re-running the iteration; the origins can start repeating one step later), so the answer does not depend on when the check noticed the repeat. An iteration whose last search starts at the range's end ends there even if that search repeats an earlier match; 0.26.0 terminates, and its answer stands. Every match returned is one the regex matched, unchanged.
   - **In range** (`match_in_range`; the differential test classifies 0.26.0's answers with the same rules): unbounded searches cover the whole buffer. A bounded one runs from its start to its end in its direction, wrapping around the buffer like the search. The match's far end may also lie in the cells read together with the character at the end (`glyph_cells`: right, the two cells after a leading spacer or the spacer after a wide character; left, the wide character of a spacer and a leading spacer before a wrapped wide character), its near end in those read with the character at the start in the other direction, and its near end must not come after its far end along the range (a match with both ends in the range in the wrong order ran around the whole buffer).
4. **`search_next`'s origin stays in the grid.** Going right, `search_next` moves its origin to the end of the character there (`expand_wide`), which for a leading spacer is column 1 of the next line. On the bottommost line (a stale spacer) there is no next line: 0.26.0 panics in debug builds and reads whatever row its ring holds there in release builds. The origin is then the cell the search lands on after reading the spacer (`glyph_end`), on the same line. 0.26.0 has no defined answer there.
5. **No panic going left from a stale spacer at column 0.** Going left, `expand_wide` moves from a wide char spacer one column back to its wide char. A stale spacer at column 0 (a resize to 2 columns and an erase leave one behind) has no column before it: 0.26.0 subtracts from column 0, which panics in debug builds and goes on from a wrapped-around column in release builds. It does so for `search_next`'s origin, and in `RegexIter` when a leftward match ends on such a spacer and the origin moves past it. Both builds now stop where the debug build panics (`Term::expand_wide_underflows`): `search_next` from such an origin answers `None`, and `RegexIter` ends before yielding that match, with `bound_fired` set, so `search_next` answers with the last in-range match yielded before it (rule 3), or `None`.

**Where answers differ from 0.26.0:** only where 0.26.0 never returns, panics or reads outside the grid (rules 2, 4 and 5), or answers with a match outside the searched range (rule 3). Wherever 0.26.0 terminates with an in-range answer, the answer is 0.26.0's (a debug build of 0.26.0: under rule 5 a release build goes on from a wrapped-around column and can answer in range where the fork, like the debug build, stops). `RegexIter` differs only by ending where 0.26.0's would repeat forever or panics.

**Costs and termination.** Neither bound is reached where 0.26.0 terminates. A search that 0.26.0 would never finish runs until its recorded state has gone round once, about twice the state's period in laps of the buffer, and that period follows the pattern: a counted pattern over long wrapped lines keeps the DFA alive with a counter (up to about 1,000 states fit the DFA cache), so `(?:[ab中]{997})*b` over a 20,000-line buffer of wrapped 100-column lines took 37 s before the check fired, about 3 minutes extrapolated to 100,000 lines, and `search_next` can run several such searches plus the reruns of rule 3. 0.26.0 never finishes there at all. A search can also end because the DFA cache gives up ("Regex exceeded complexity limit" in the log, and no match), as in 0.26.0. That give-up is also what makes the loop check exact and finite: the search never reports progress to regex-automata's cache, so the cache counts as inefficient and gives up on its fourth clear (`minimum_cache_clear_count(3)` and `minimum_bytes_per_state(10)` in `RegexSearch::new`, regex-automata 0.4.11), which caps the clears at 3 and keeps the recorded state finite. `cache_give_up_ends_a_search` pins it under a timeout. An iteration that 0.26.0 repeats forever runs about one to three times its cycle before the check notices it, and the answer then re-runs it up to twice.

- Tests: `wrapped_wide_*`, `empty_pattern_terminates`, `stale_leading_spacer_*`, `stale_spacer_*`, `range_ending_on_*`, `search_origin_on_bottom_line_stale_spacer`, `stale_spacer_column_zero_*`, `repeat_from_range_end_ends_iteration`, `left_match_past_range_start_wrapping`, `left_iteration_stops_where_upstream_stops`, `regex_iter_ends_where_upstream_repeats`, `rereview_*`, `counted_pattern_hits_the_cycle_check` and `cache_give_up_ends_a_search` in `src/term/search.rs`, with timeouts so a regression fails instead of hanging. Their expected values are 0.26.0's, recorded from the differential test's oracle, where 0.26.0 answers in range; `RegexIter` tests check 0.26.0's endless sequence up to the bound. `wrapped_wide_fuzz` runs every search over 2- to 4-column grids with wrapped and stale leading spacers, with and without scrollback, and checks that all of them end and that `search_next` answers inside its range. In `tests/differential.rs`, `search_soak_regressions` replays the soak seeds and `search_grid_probe` compares `search_next` with 0.26.0 on hand-built small grids written into both crates. Where 0.26.0 has no in-range answer, the differential test walks 0.26.0's own iteration up to its first repeated match, its end or its panic (rule 5, treated as a panic in release builds too), and requires feathercritty's answer to equal the one rules 3 and 5 pick from that walk (`check_search_walked`, `Walk::answer`). `search_grid_probe` writes stale spacers at any column, so it reaches rule 5.
- When merging upstream: if `regex_search_internal`, `skip_fullwidth`, `RegexIter` or `next_match_left`/`right` changed, keep this change's additions (the loop check and `LoopState`, the iterator's cycle check and its stop at `expand_wide_underflows`, `final_match`) in step with what the code reads and chooses; if upstream's `expand_wide` stops subtracting from column 0, drop rule 5 and the differential test's matching workaround in `search_terminates`; the `// feathercritty:` comments name each. If upstream bounds its loops and keeps answers in range itself, drop this change, re-run the tests above and the differential test. Re-check termination (run `cache_give_up_ends_a_search` and `counted_pattern_hits_the_cycle_check`) on a regex-automata update, if `RegexSearch::new` changes the cache config, or if upstream starts reporting search progress to the cache (`Cache::search_start`/`search_update`): the loop check relies on the cache giving up on its fourth clear.
- Not changed (0.26.0 behavior, so the differential test compares it):
  - On 2-column grids, the right step from column 0 over a leading spacer to column 1 also looks like a line break to `regex_search_internal`'s line-break check, which resets the match.
  - A stale leading spacer reads differently by direction: going right, the search reads the next cell in its place and skips the cell after that; going left, it reads a blank. The two searches of one match can then disagree; the match fails or ends past its origin.
  - The line-break check compares the cells the search lands on, after the fullwidth skip. A line that ends in a wide character's spacer without wrapping, followed by a line that starts with a wide character, therefore reads as one line, and a match can span the two lines (differential soak seed `realistic_cjk` 1000223).
  - When the bottom line wraps (its last cell has `WRAPLINE`), the search reads on from it into the top line, so a match can run around the buffer's end and start after its end in grid order (differential soak seed `random_streams` 1000017).

### 6. Screen and history split (explicit history reads)

`0.26.0+fbterm.4`. Phase 1 of the compact scrollback work: the grid keeps the visible screen and the scrollback in two containers, and every read of scrollback goes through an explicit API. The scrollback is still dense (a `VecDeque` of `Row`s) in this release, so memory use and speed are about what 0.26.0 had (ingest within about 4%, one alternate-screen row 1.7% slower; see the benchmark note below and `benches/RESULTS.md`); the point is the API, which lets a later release store history compactly without changing callers.

**API**
- `Grid<T>` is `{ screen: Screen<T>, history: History<T> }`. `Grid::screen()` and `Grid::screen_mut()` return the screen, a handle over upstream's `Storage` ring that implements `Index`/`IndexMut` for `Line` and `Point` with upstream's `debug_assert!` range checks. The `max_scroll_limit` field is now `history.limit()`.
- **`Grid` itself no longer implements `Index`/`IndexMut`.** Indexing is screen-only (`grid.screen()[line]`, lines `0..screen_lines`). History lines (negative `Line`) are read through:
  - `RowReader<T>`: `RowReader::new()` and `reader.row(&grid, line) -> &Row<T>` for a whole row of screen or history. Keep one reader and reuse it; a later release decodes history rows into its scratch row.
  - `Grid::cell(point) -> T` (an owned cell), `Grid::wraps(line) -> bool` and `Grid::is_clear(line) -> bool`, for single reads that work for screen and history lines.
- `GridIterator` yields `Indexed<T>` by value (it used to borrow `&T` from the grid). `GridIterator::cell(&self) -> &T` borrows the current cell without cloning; `advance`/`retreat` (`pub(crate)`) step without producing an item.
- `History<T>` (`src/grid/history.rs`, new) owns the scrollback: `new`, `len`, `is_empty`, `limit`, `set_limit`, `push_newest(&Row)`, `pop_newest`, `pop_oldest`, `read`, `update`, `wraps`, `is_clear`, `clear`. Cells stored in it implement the public `HistoryCell` trait, defined in `src/grid/compact.rs` with the row codec (change 7).
- The only write to history outside scrolling and resizing is the one in `Term::input` (`Grid::update_history_row`).
- (Phase 1 only: `History::push_newest_recycle` swapped the departing screen row for a recycled one in `scroll_up`. Change 7 replaced it with `push_newest` plus the in-place reset upstream does.)
- serde form is unchanged: the same fields as upstream (`raw.inner` from the bottom line up, `zero` 0, `len`, `visible_lines`, the scroll limit), through private proxy structs. Deserialization splits at the grid's `lines`, because old reference files carry a stale `visible_lines`. `tests/ref/` data is unchanged.

**Merging a new upstream release.** Upstream code that indexes the grid (`self.grid[point]`, `grid[line]`, `grid.raw`-style access) will not compile after a merge. Classify each site:
- *Screen*: the line is always `0..screen_lines` (handler writes, cursor, the visible region). Use `grid.screen()` / `grid.screen_mut()`.
- *History-capable*: the line can be negative (selection text, search, vi motions, anything that follows a point or a neighbouring line). Use `Grid::cell`, `Grid::wraps`, `Grid::is_clear`, a `RowReader`, or `GridIterator`.

The sites classified as history-capable in 0.26.0: `Term::line_to_string`, `Term::expand_wide`, the vi cursor in `RenderableCursor`, in `search.rs` `regex_search_internal`, `glyph_cells`, `skip_fullwidth`, `bracket_search`, `inline_search_right`, `line_search_left`/`line_search_right`, in `vi_mode.rs` `ParagraphUp`/`ParagraphDown` and `semantic` (`expand_semantic`, `is_space`, `is_wrap`), and every `GridIterator` user (`display_iter`, `clear_viewport`, the regex, bracket, semantic and inline searches). Everything else is screen.

**Behavior changes made with it** (both are also patched into the differential test's oracle, see Development)
1. *`Row` `occ` invariant* (`src/grid/row.rs`, `Row::grow` and `Row::append`). Upstream documents that all cells after `occ` are equal, and `Row::reset` relies on it, but `grow` padded with default cells without raising `occ`, and `append` did `occ += n` even when `occ` was below the old length. A reset could then leave stale cells behind, and what a recycled row looked like depended on which physical row the ring had recycled.
   - Before: `grow` left `occ` alone; `append` set `occ += vec.len()`.
   - After: `grow` first sets `occ = max(occ, len)`; `append` sets `occ = len + vec.len()` when `vec` is not empty.
2. *Reads outside the grid are "no row"*. 0.26.0 read lines just outside `topmost_line()..=bottommost_line()` in a few places: debug builds failed a `debug_assert!`, release builds read whichever row the ring held there (a cache row or a wrapped-around screen row).
   - `Term::line_to_string`. Before: a selected line ending in a leading wide-char spacer appended `grid[line - 1][Column(0)].c`, even on the topmost line. After: it adds nothing above the topmost line.
   - Vi motions. Before: the cursor could leave the grid (`Middle` on a one-line screen without history, `Right`/`Last` across a wrap or leading spacer on the bottom line). After: `ViModeCursor::motion` clamps the point into the grid (`grid_clamp(term, Boundary::Grid)`).
   - Iterators and readers. Before: undefined (see above). After: `Grid::cell` and `GridIterator::cell` return a default cell, `Grid::wraps` returns false, `Grid::is_clear` returns true. `RowReader::row` and the `History` methods keep a `debug_assert!` (a caller bug) and in release return default cells of the grid's width, a no-op, false and true.

**Other changes**
- `Storage::initialize` grows by exactly the rows needed (upstream added at least 1000 at a time, a history cache); it keeps upstream's hidden rows beyond `len`, which `scroll_up` recycles. (Phase 1 also had a small spare-row pool there; change 7 removed it, the history's block pool does that job.)
- `Grid` equality compares content, including history.
- `Grid::scroll_up` moves the departing rows into history, then rotates and resets as upstream did.
- `resize.rs`: `grow_lines` moves popped history rows onto the new top rows and removes only the rows `scroll_up` pushed; it clamps the display offset unconditionally (upstream's `decrease_scroll_limit` always clamped). Column reflow collects screen and history into one `Vec` and splits it back (change 7 streams it instead). Every container call that differs from upstream carries a `// feathercritty:` comment, so the algorithm text can be diffed against upstream.

### 7. Compact history

`0.26.0+fbterm.5`. The scrollback is stored compactly: every row that scrolls off the screen is encoded once into a byte record, and records are packed into pooled 64 KiB blocks. The visible screen stays a dense ring of `Row`s, exactly as upstream, so the parser's write path is unchanged; history rows are decoded only when something reads them, through the explicit read API of change 6. A full 10,000-line history of short lines takes 0.68 MB instead of about 31 MB. Behavior is unchanged: the differential test compares every cell and query answer with 0.26.0.

**Credit.** The idea of keeping the visible screen dense while storing history rows in a compact form, with pooled buffers and an explicit history read API, comes from Adam Mikołajczyk (Razuer), who proposed it in alacritty/alacritty#9049. feathercritty's implementation is independent and was written from the idea only.

**Format** (`src/grid/compact.rs`, module docs "Record format"; the authoritative description)
- A record is a header (`W` width, `P` cells stored explicitly, `R` runs, `M` marks, `E` extras, as LEB128 varints, plus a bits byte with `WRAPS` and `CLEAR`), the text of cells `0..P` as UTF-8 (one char per cell), the attribute runs (length, fg, bg, flags, extra reference), the marks (column deltas with the structural flags: wide character, spacers, `WRAPLINE`) and the tail cell, which every cell from `P` to `W-1` equals. Trailing blanks and background-colored erased tails cost one tail record.
- Colors are 4 bytes; vte's named colors are written as explicit codes, so a vte renumbering does not change the format.
- `CellExtra` values (zero-width characters, underline color, hyperlinks) stay `Arc`s in one typed queue per history; records refer to them by position, once per run. Records hold no pointers or process-specific values, so blocks could later be written to disk as they are.
- Typical sizes at 126 columns: a short line about 49 bytes, a colored log line about 194 bytes, a dense line about 1.6 KB (0.26.0: 3,024 bytes for every row).

**Store** (`src/grid/history.rs`, module docs "Layout", "Invariants", "Eviction and the pool")
- Records are appended to 64 KiB blocks and never span two; a record above a quarter block gets its own block. Rows are encoded straight into the newest block when it surely has room (`HistoryCell::max_record_bytes`), else through a reused scratch buffer.
- One 16-byte index entry per row. The index grows by doubling up to the limit, so a full history's index holds at most `limit` entries; after a column reflow it can hold up to `limit + lines` (the reflow builds the new history with upstream's `limit + lines` and lowers the limit without shrinking the index).
- Spare blocks: a block whose last row is evicted becomes a spare, and the history keeps **at most 2** (`MAX_SPARES`); new blocks come from the spares first, so steady scrolling with a full history allocates nothing. `clear` and a lower limit (`set_limit`) free what they no longer need and also keep at most 2 spares. The library never calls into the allocator to return memory to the OS; that is the host's decision.
- Block size: 64 KiB. Measured between 16 and 256 KiB in the tuning pass (`benches/RESULTS.md`, "Block size"): larger blocks did not help dense rows, helped short lines at 200x60 only slightly (1.23 to 1.19), cost memory (log lines 2.13 MB at 64 KiB, 2.52 MB at 256 KiB) and moved the zero-allocation steady state further out.

**API** (additions to change 6; existing callers compile unchanged)
- `HistoryCell` (public, `src/grid/compact.rs`; it used to be an empty trait implemented in `src/term/cell.rs`): `type Extra`, `row_wraps`, `encode`, `decode` (returns the bytes consumed), `decode_cell`, and, with defaults, `max_record_bytes` (`None`) and `reflow_info` (`None`). `Grid<T>` requires `T: HistoryCell`; `Cell` implements it in `compact.rs`.
- `RowHeader` appears in the public trait (`encode` returns it) but lives in a private module (it cannot be named outside the crate) and its fields are crate-private: an implementation outside the crate can only return `Default::default()`, not a correct header, so in practice only this crate's cell types implement `HistoryCell`. Treat `RowHeader` as part of the public surface when changing it. `ReflowInfo` (re-exported from `grid`) likewise has crate-private fields and no constructor, deliberately: only the crate's own `Cell` format opts into the reflow byte copy, and an outside implementation keeps the default `reflow_info` (`None`).
- `RowReader` and `GridIterator` decode a history row into their own scratch row once per row (screen rows are lent in place); `Grid::cell` decodes only the cell asked for.
- Cargo feature `test-hooks` (off by default, not a stable API; the crate's own tests enable it through a self dev-dependency): `Grid::new_with_block_size`, `Grid::set_reflow_window` and `Grid::set_reflow_byte_copy`.

**Behavior.** Unchanged against 0.26.0 (with the oracle patches of change 6), with one internal exception that has no visible effect: `Term::clear_line` lowers a row's `occ` after an erase that reaches the end of the line (`Row::set_equal_from`); `Row::reset` then writes the same cells it would have.

**Resize** (`src/grid/resize.rs`, design spec 5.6). The column reflow is upstream's algorithm line for line over two streaming containers: `RowSource` stands for upstream's `take_all()` `Vec` and pops old history rows oldest first, freeing old blocks as it goes; `ReflowSink` stands for upstream's `reversed`/`new_raw` `Vec` (`push`, `last_mut`, `len`, `truncate_newest`, `resize_with_blank`, `finish`), keeps the newest `2 * lines + 2` rows dense and encodes older rows into a new history, decoding rows back when an operation reaches past that window. Peak memory is the old plus the new compact store. History rows the loop would push unchanged but for their width skip the loop and are copied as bytes with only `W` changed (`RowSource::next_reflow`, `Pass::byte_copy_width`). Those conditions are a correct superset of the text of spec 5.6, each refinement taken from upstream's loop: shrinking accepts any empty tail (`GridCell::is_empty`, which is what `Row::shrink` drops), not only the default cell; shrinking without reflow copies too (the loop pushes the cut row either way); and growing uses upstream's whole `should_reflow` (`reflow`, `len < columns`, wrapping last cell), not only "the previous row does not wrap". `byte_copy_width_only_when_the_loop_keeps_the_row`, `reflow_window_one_matches_default` (window 1, byte copy on and off) and the differential test check them.

### 8. Grapheme clusters (mode 2027)

`src/term/mod.rs`, new `src/term/cluster.rs`, `Cargo.toml`. Some characters are built from several code points: flags (two regional indicators), skin tones (base plus modifier), joined emoji (pieces joined by ZWJ) and a presentation chosen by a variation selector. 0.26.0 handles one code point at a time: zero-width ones attach to the previous cell, every visible one takes cells of its own, so a flag or a joined emoji spreads over several cells. With DEC private mode 2027 set, each grapheme cluster lives in one cell instead.

- **The mode.** `TermMode::GRAPHEME_CLUSTER`, set and reset with `CSI ? 2027 h` / `l` (vte 0.15 has no named variant, so `PrivateMode::Unknown(2027)`) and reported by DECRQM (`CSI ? 2027 $ p` answers set or reset instead of not supported). `Config::grapheme_clusters` (default `false`) is its value when the terminal is created and after a full reset (`RIS`); `set_options` never flips it on a live terminal, and `Term::reset_grapheme_cluster_mode` restores the default for a new program taking over an existing terminal.
- **While it is reset nothing changes.** `Term::input` takes the 0.26.0 path untouched, and so does every code point at or below U+00FF and every code point at column 0 without a pending wrap while it is set. The differential test (which never sets the mode) compares like for like.
- **Joining.** For a code point that may join, the previous cell (the cell left of the cursor, the cursor cell under a pending wrap, the wide character left of a spacer) is checked for an extended grapheme cluster boundary (UAX #29, `unicode-segmentation`) between its base plus joined pieces and the new code point. The state is rebuilt from the cell each time, so a cluster split across reads joins the same, and pieces stored before the mode was set are taken into account. No boundary: the code point is stored with the cell's pieces (`Cell::push_zerowidth`, as zero-width characters are). A boundary: it prints as usual, except that a zero-width code point with nothing to join is dropped. A space (blank or written, whatever its style) takes zero-width marks, as without the mode, but never a visible joiner. A quick check skips the segmentation when both code points come from ranges that never join (CJK, kana, Hangul syllables, box drawing, fullwidth forms; a test checks every one against the segmentation), and the segmentation runs on a stack buffer, so non-Latin output with the mode set costs about a quarter more than with it reset, and nothing changes while it is reset. A cell holds at most 32 joined pieces (`MAX_CLUSTER_PIECES`); further ones are dropped.
- **Width.** VS16 widens and VS15 narrows a base with emoji variation sequences (a table of the 371 bases in Unicode 17.0.0 `emoji-variation-sequences.txt`, the Unicode version of `unicode-width` 0.2.2); a variation selector after any other base changes nothing. Any other joining code point that is not zero-width on its own widens the cluster. Widening writes a spacer in the next column (in insert mode it shifts the rest of the line right by one, clearing a wide character cut at the end); in the last column the cluster moves whole to the next line behind a leading spacer, as a wide character does, or stays narrow without line wrap. Narrowing clears the spacer (in insert mode the line moves back left) and moves the cursor back; a cluster that had moved to the next line because it turned wide moves back to the end of the line above, with the wrap pending. A one-column terminal keeps clusters narrow, and a cluster moved at the edge keeps its own colors, attributes and hyperlink.
- **Dependency.** `unicode-segmentation` (MIT or Apache-2.0).
- **Tests.** `src/term/cluster.rs` (boundaries, width effects) and the `clusters` module in `src/term/mod.rs`: the mode and its report, joining (flags, skin tones, ZWJ sequences, selectors, split reads, the cap, the mode set midway), the edges (last column with and without wrap, pending wrap, insert mode), overwriting half a cluster, and clusters kept through the compact history and a reflow.

### 9. Cold history compression

`0.26.0+fbterm.7`. Opt-in: history blocks far enough from the newest row are kept compressed ("cold"), so a long scrollback of ordinary output takes a fraction of the memory of change 7. With the option off (the default) nothing changes. featherbit terminal lets users keep up to millions of history lines per tab, and on realistic output (build logs, service logs, shell sessions) the compact records of change 7 still compress about 4 to 9 times; this change takes that saving without touching the parser's path or the read API.

**What** (`src/grid/history.rs`, module docs "Cold blocks"; `src/grid/cold.rs`)
- `Config::history_compression: Option<usize>`: keep that many of the newest history rows uncompressed and compress every block whose rows are all older (`None`, the default, never compresses; any value is accepted, 0 included). `Term::set_options` applies it to both grids, like `scrolling_history`. The newest block is never cold.
- A cold block is the zstd level 1 frame of the block's bytes behind a one-byte format tag and the uncompressed length (`cold.rs`). Index entries are unchanged: an offset still counts in the uncompressed bytes. The compressor was chosen by measurement (`benches/RESULTS.md`, "Compressor choice"): the `zstd` crate (MIT or Apache-2.0), the only candidate that met the memory gate on every corpus.
- Blocks change state only through jobs, never inline, so the host decides where the work runs: `Term::has_history_jobs` (O(1)), `Term::next_history_job` and `Term::next_history_jobs(max)` (a copy of one or up to `max` blocks, taken under the terminal's lock), `HistoryJob::run` (compresses or decompresses the copy, no lock needed), `Term::install_history_job` (swaps the result in under the lock; never compresses or copies). `Term::run_history_jobs` runs everything inline (tests, hosts without a worker).
- Reads decompress through a cache of at most 4 blocks per history (`RefCell`; `History` stays `Send`); `Term::drop_history_cache` frees it after a sweep (search, export). `wraps` and `is_clear` answer from two bits in the index entry and never decompress.
- A column reflow builds the new history warm and leaves its compression to jobs afterwards; it reads each old cold block once and frees it as its last row leaves.

**Why.** History memory at long scrollback is dominated by block bytes once change 7 has made rows compact; realistic output repeats itself (paths, timestamps, log templates, colors) and compresses well per 64 KiB block. Doing the work in jobs keeps the parser's lock holds short and lets a host run them on a low-priority thread.

**Invariants** (the module docs of `history.rs` are authoritative)
- Eligibility: a block should be cold when compression is on, it holds rows, none of them is among the `keep_warm` newest, and it is not the newest block; while the history is full, a warm oldest block stays warm (its rows are the next to be evicted, so compressing it frees nothing; with `keep_warm` just below the limit no block is ever compressed). Per-block warm counts make this exact; they are kept only while compression is on.
- Identity rule: a job carries its history's process-unique id, the block's sequence number and generation (from a counter that never repeats). `install` refuses a job from another history, for a block that changed, was evicted or cleared, or under another setting; the grid's history epoch refuses jobs taken before a reflow. Refused results are dropped and the block is offered again.
- Off means off: with `None` and no cold block left there are no jobs, and the added paths cost one `Option` or `cold` check each. Reads reach records through a closure (`with_record`), and stored entries take their header bits from the encoder, so warm reads and the byte-copy reflow run as fast as before.
- A cold block whose last row goes is freed (never kept as a spare); a cold block that becomes the newest again is decompressed at once; `update` of a cold row re-encodes it into the newest block.

**Changed upstream files, and what to watch when merging.** Nothing upstream corresponds to this change.
- `src/term/mod.rs`: the `Config` field, `set_options` applying it, and the job API (`HistoryJob`, `HistoryDone`, `has_history_jobs`, `next_history_job`, `next_history_jobs`, `install_history_job`, `run_history_jobs`, `drop_history_cache`). An upstream change to `Config` or `set_options` only needs the field carried along.
- `src/grid/mod.rs`: `set_history_compression`, the history epoch, `history_plain_text` taking a closure (a cold record lives in the cache only while it is read), and test hooks. `src/grid/resize.rs`: the reflow's new history is the old one's `sibling` (same block size and setting).
- New: `src/grid/cold.rs`. `src/grid/history.rs` gained the cold state, the cache, the job API and its tests. `Cargo.toml`: the `zstd` dependency, without default features.
- Tests and benchmarks: `tests/corpora/` (three seeded generators and two recorded streams), `tests/compress_choice.rs`, compressed variants in `tests/large_history.rs`, `tests/alloc.rs` and `tests/differential.rs` (`DIFF_COLD`, jobs run, dropped or held across steps), and the compression sections of `benches/ingest.rs` and `benches/reads.rs`.

**Measured results.** At 1,000,000 history lines of realistic output (build and service logs, shell sessions, recorded streams), the history takes about a quarter to just over a third of its memory with compression off (Apple M5 Max, release). Memory at 100,000 lines and for random content, search, read, reflow and ingest speed, the worker's lock holds and the cost of switching are measured against their gates in `benches/RESULTS.md`, "History compression", with the method and commands.

**Open items for the owner** (the gates are unchanged; numbers and reasoning in `benches/RESULTS.md`, "History compression"): with compression off, some rows sit slightly above the fork's `main` in some sessions, and live bytes are slightly higher per block slot; with it on, parser-side ingest is borderline at its gate, the reflow comes slightly above "off plus one decompression of the old history", and switching on briefly goes about two blocks above the uncompressed size before it comes down.

### 10. Vendored VT parser with OSC string caps

`src/vte/` (new): feathercritty now carries its own copy of the `vte` 0.15.0 parser instead of depending on the crate, so it can cap string sequences without waiting for upstream. Changes 10 to 16 are the inline-images work and ship together under `0.26.0+fbterm.8`.

**The copy.** `src/vte/mod.rs`, `src/vte/ansi.rs` and `src/vte/params.rs` are copies of vte 0.15.0's `src/lib.rs`, `src/ansi.rs` and `src/params.rs`, with the module paths adjusted (`crate::` becomes `crate::vte::`) and built for feathercritty's always-`std`, always-`ansi` configuration: the `no_std` / fixed-buffer branches are dropped (the parser always uses `Vec`), and the `serde` derives follow this crate's own `serde` feature. Each copied `.rs` starts with `// Copied from vte 0.15.0 (Apache-2.0 OR MIT) by the featherbit authors for feathercritty; see README.md for the list of changes.`; upstream provenance comments are kept as they were. `src/vte/LICENSE-APACHE` and `src/vte/LICENSE-MIT` are verbatim copies of the upstream license files, so (like the vendored oracle) they carry no notice line. vte's own tests move with the source and run as unit tests.

**Caps.** `Parser` gains two limits on OSC strings:
- `MAX_OSC_BYTES` (`64 * 1024`, public): once an OSC string reaches it, it stops collecting bytes and is discarded (not dispatched). This bounds the buffer against a never-terminated oversized OSC. Nothing is exempt — an inline image's payload never enters the buffer at all (it streams straight to the handler) and its arguments have their own smaller limit (`MAX_OSC_STREAM_ARGS`, `4 * 1024`), so a `1337` string is capped exactly like any other.
- Parameters past `MAX_OSC_PARAMS` (`16`) are kept in the last parameter instead of dropped, so a `1337` command with more than 16 `;`-separated arguments keeps its later ones.

**Streaming.** Three string sequences go to the `Perform` implementation as they arrive instead of into the parser's buffers, so a large payload costs no parser memory (the module docs name the states and the callbacks):
- APC content (`ESC _ ... ESC \`), the kitty graphics protocol's transport: `apc_start`, `apc_put`, `apc_end`, and `apc_abort` when it ends early.
- An OSC 1337 inline image (`ESC ] 1337 ; File = <args> : <data>`): everything after the first `:` streams to `osc_stream_put` and never enters the OSC buffer. `osc_stream_start(args)` is dispatched once a `:` appears, with at most `MAX_OSC_STREAM_ARGS` (`4 * 1024`) bytes of arguments; arguments that pass that cap before any `:` abort the sequence with **no start dispatched** (`osc_stream_abort`), so a handler never sees half a header, and the payload streams past as discarded bytes.
- Device control strings: the bytes vte hands over one at a time are collected into runs and passed with `put_slice`. A DCS whose final byte is `q` with no intermediates (sixel) streams its parameters to `Perform::hook` and its data to `put_slice`; every other DCS keeps vte's `hook`/`put`/`unhook`, which nothing here acts on.

Only `ST` (`ESC \`) completes a streamed string: a bare `ESC`, `CAN` or `SUB` inside one aborts it, and nothing is dispatched — for a DCS that shows up as `unhook_cancelled` rather than `unhook`. A read can end between an `ESC` and the `\` that completes its `ST`, so the parser carries that one byte to the next read: the buffered `ESC` ends the string if the next byte is `\` and aborts it otherwise, and that byte is then handled as the start of an escape sequence. `ESC ESC \` (an aborted string followed by a literal `ST`) therefore aborts with its first `ESC`, and cutting a stream at any byte dispatches exactly what the whole stream would. SOS (`ESC X`) and PM (`ESC ^`) stay discarded, as in vte: nothing is collected for them and no terminator dispatches anything.

**Public paths unchanged.** `feathercritty::vte::{Parser, Perform, Params, ParamsIter}` and `feathercritty::vte::ansi::*` are the same as the old re-export of the crate; `src/lib.rs` now has `pub mod vte;`. `src/event_loop.rs` is the only file that named the dependency crate directly (`use vte::ansi;`) and now uses `crate::vte::ansi`. The additions are defaulted trait methods, so existing implementations compile unchanged: `Perform` gains `apc_start`/`apc_put`/`apc_end`/`apc_abort`, `osc_stream_start`/`osc_stream_put`/`osc_stream_end`/`osc_stream_abort`, `put_slice` and `unhook_cancelled`; `Handler` gains the matching graphics callbacks (`apc_*`, `sixel_start`/`sixel_put`/`sixel_end`/`sixel_abort`, `inline_image_start`/`inline_image_put`/`inline_image_end`/`inline_image_abort`) plus `graphics_attributes` (XTSMGRAPHICS) and `cell_size_pixels` (`CSI 16 t`). The blanket `Perform` implementation for a `Handler` routes APC frames to the `apc_*` callbacks, an inline image's stream to `inline_image_*`, sixel runs to `sixel_put`, a cancelled string to `sixel_abort`, and a hook for a DCS whose final byte is `q` with no intermediates to `sixel_start`; every other DCS keeps vte's own messages.

**Cargo.toml.** The `vte` dependency is gone; `cursor-icon` and `memchr` are added (with `bitflags`, `log` and `serde` already present) — the dependencies the copy needs for its `std` + `ansi` build. ### 11. Graphics payload plumbing (`src/graphics/b64.rs`, `src/graphics/limits.rs`)

`0.26.0+fbterm.8`, new. The pieces the two protocols that carry base64 payloads share (changes 12 and 14), and the caps they read. Both are crate-internal except the limits, which hosts use to size their own caches.

**Incremental base64** (`b64.rs`, `pub(super)`). A payload arrives in arbitrary slices and must decode as if it had arrived whole. At most three characters — an incomplete quad — are carried between slices; a final group is accepted with or without its padding. Padding **ends** the payload: data after it is refused whether it arrives in the same slice as the padded group or in a later one, because a sender that pads every chunk of one blob is not sending base64 and guessing at those bytes would store an image whose content depends on where the reads were cut. An empty slice after padding is not data and completes the payload unchanged. The size a slice decodes to follows from its length, so `put` and `finish` take the room their caller has left and answer `TooBig` before producing any bytes; that figure is the rounded-up 3/4 with the shortening padding taken back out, so a payload that fits is never refused for rounding. Anything outside the protocol's alphabet, or a final group too short to carry a whole byte, is `Invalid`.

**Caps** (`limits.rs`, public): `MAX_IMAGE_SIDE` 10 000 pixels per axis; `MAX_IMAGE_BYTES` 64 MiB, one RGBA8 frame — what an embedder decodes into; `MAX_PAYLOAD_BYTES` 16 MiB of decoded payload for one transmission or file; `STALL` 10 s without progress. Every buffer in `src/graphics/` is bounded by these, and every size computation is saturating arithmetic (`u32`/`u64`, no multiplication overflow), so remote input cannot make the parser panic, hang or grow without bound. This fork never reads local files: file-based media is refused rather than fetched (change 12).

### 12. Kitty graphics protocol (`src/graphics/kitty.rs`)

`0.26.0+fbterm.8`, new. `KittyParser` is fed by the APC callbacks of change 10 (`apc_start` → `start`, `apc_put` → `put`, `apc_end` → `end(now)`, `apc_abort` → `abort`) and turns a sequence `ESC _ G <control data> ; <base64 payload> ESC \` into a `KittyCommand`. APC content that does not start with `G` is a foreign APC: consumed and ignored without a reply. The control data is a comma-separated list of `key=value` pairs; the first `;` ends it and everything after is payload text. A key sent twice keeps its last value.

**What it accepts.** Direct and chunked transmission (`t=d`, `m=1`/`m=0`) of raw RGB and RGBA (`f=24`/`f=32`) and PNG (`f=100`, sized from its header), optionally zlib compressed (`o=z`, inflated incrementally). Transmissions (`a=t`), transmissions that place (`a=T`), displays of a stored image (`a=p`) and the support query (`a=q`). Placements take a cell span (`c` columns by `r` rows, either one left at 0 to mean "compute from the image's pixels and the other axis"), a source rectangle in image pixels (`x`, `y`, `w`, `h`, a zero side meaning "to the end"), pixel offsets inside the anchor cell (`X`/`Y`), a z-index (`z`, negative draws under text), a placement id (`p`: re-placing with the same image and placement id replaces the old placement), virtual placements (`U=1`, change 15) and the cursor movement policy (`C=1` places without moving the cursor). Chunked payloads accumulate across APC sequences keyed by `i` or `I`; a continuation frame may carry only `m`, `q` and the `i`/`I` naming the transmission it belongs to, so a frame carrying any other key starts a new transmission and silently abandons an unfinished one, as the protocol requires.

**What it refuses, and with what code.** File-based media `t=f` and `t=t` (and `t=s`) with `EBADF`; indexed color formats `f=8`/`f=16` and the animation actions `a=f`, `a=a`, `a=c` with `ENOTSUPPORTED`; anything malformed — an unknown or unsupported key (`S`, `O`, `N`, `e`, `P`, `Q`, `H`, `V`, `F` among them), a bad value type, both `i` and `I` in one frame, an out-of-range integer, a truncated compressed stream, raw data that does not match its declared size (compressed data longer than declared is refused without inflating the excess) — with `EINVAL`; images over the caps of change 11 and transmissions past `MAX_PAYLOAD_BYTES` with `ENOMEM`, where a raw format's declared size counts four bytes per pixel whatever `f` says, because `f=24` is expanded to RGBA before the host sees it; PNG data whose header is missing or unreadable with `EBADPNG`. A transmission with no payload decodes to nothing and is silently ignored: there is no image to store or place. `a=q` is checked exactly like the transmission it asks about, so a client probing which transfer media work gets `EBADF` for the ones this terminal will not accept instead of an `OK` that every later image would contradict.

**Replies.** Rejections do not travel as commands: they wait in a one-slot side channel (`take_reject`) until the caller answers them with `kitty::reply`, which writes `ESC _ G <code>[;i=<id>][,I=<number>][,p=<placement>] ESC \` — echoing the id it assigned and, for an image addressed by number, the number too. A placement id travels only with an image id, and a successful `a=T` echoes the placement id its frame carried (`i=7,p=3;OK`). A transmission addressed only by number has the terminal assign it an id — the smallest unused nonzero one — echo that too (`i=<new>,I=<n>;OK`) and store the image under it, so a later `a=p` or `U=1` placement can name it. The protocol ties acknowledgements to an image id: a command carrying neither `i` nor `I` gets **no reply at all** — such clients do not read one, and bytes written anyway land in the program's stdin or at the shell prompt after it exits. `q=1` suppresses a successful answer, `q=2` suppresses every answer; failures survive `q=1`. Bad control data never disturbs a chunked upload in progress: only a payload failure, a delete command or a frame that starts another transmission ends one (the protocol asks a delete to abort an upload).

**Deletion.** `a=d` with the protocol's selectors: `d=a`/`A` every placement on screen, `d=i`/`I` one image (optionally one placement of it), `d=n`/`N` the newest image with a number, `d=c`/`C` placements under the cursor, `d=p`/`P` and `d=q`/`Q` placements intersecting a cell (at a z-index), `d=x`/`X` a column, `d=y`/`Y` a row, `d=z`/`Z` a z-index, `d=r`/`R` an id range. The uppercase forms free the stored image as well as its placements. The cell- and column-addressed selectors (`d=p|q|x`, upper and lower) name 1-based coordinates: a missing or zero `x` (or `y` for the cell forms) is refused with `EINVAL` rather than subtracted through zero downstream.

**Time and bounds.** `end(now)` and `tick(now)` drop a transmission that has made no progress for `STALL` with `ENOMEM`, so an idle terminal releases a client that stopped mid-upload; time is injected, so tests never sleep. Every buffer is bounded: one control pair by `PAIR_CAP` (64 bytes — every supported value is at most eleven ASCII bytes), the staged payload of one frame and the accumulated bytes of one transmission by `MAX_PAYLOAD_BYTES`, the inflated output by `MAX_IMAGE_BYTES` or, for a declared raw format, by its own declared size; the inflate buffer is 64 KiB (`INFLATE_SPARE`). A dropped transmission releases what it held.

**Tests.** `src/graphics/kitty_tests.rs`: `parses_all_keys`, `chunked_transmission_across_sequences`, `base64_split_mid_quad`, `padding_in_a_later_chunk_is_refused`, `zlib_payload_inflates_within_cap`, `zip_bomb_is_enomem`, `file_media_is_refused_ebadf`, `oversized_header_is_enomem`, `endless_transmission_is_dropped_at_cap`, `stalled_transmission_is_dropped` and `tick_drops_stalled_transmission`, `reply_quiet_levels`, `garbage_keys_are_einval`, `non_graphics_apc_is_ignored`, `png_format_rules`, `delete_aborts_partial_upload`, `query_reports_refused_media`, `a_second_start_abandons_the_unfinished_frame`, `bytes_after_a_finished_zlib_stream_are_dropped`, `compressed_raw_data_longer_than_declared_is_einval`, `compressed_output_is_capped_at_the_image_limit_not_the_payload_cap` and `rgb_declared_size_is_checked_as_rgba`.

### 13. Sixel (`src/graphics/sixel.rs`)

`0.26.0+fbterm.8`, new. `SixelDecoder` decodes the DEC VT330/VT340 graphics format (volume 2, chapter 14 of the terminal specification) into RGBA8. It is fed by change 10's sixel callbacks: `sixel_start(params)` builds it with the DCS parameters in front of the `q` (`P1`, `P2`, `P3` positional; only `P2` changes decoding), each `sixel_put` feeds `put`, and both `sixel_end` and `sixel_abort` call `finish` — a truncated stream decodes as far as it got, which is what the format asks of an aborted canvas.

**Decoding.** Sixel characters `?` to `~` each encode six vertical pixels with the least significant bit at the top; `!Pn` repeats the last pattern `Pn` times; `$` is the graphics carriage return and `-` the graphics newline; `"Pan;Pad;Ph;Pv` sets raster attributes, whose `Ph`/`Pv` declare a minimum size and allocate nothing up front (a 15-byte header may declare 10 000×10 000 without reserving for it before the first sixel); `#Pc` selects a colour register and `#Pc;Pu;Px;Py;Pz` defines one (`Pu=2` RGB with channels 0-100, `Pu=1` HLS with hue on the DEC wheel — 0° blue, 120° red, 240° green — and lightness and saturation 0-100), which also selects it. Each image gets its own private set of 1024 registers (`REGISTERS`, what XTSMGRAPHICS reports); registers 0 to 15 start as the VT340 factory-default colour map, the rest undefined. Pixels are square: the aspect parameters say how a terminal *displays* the image and change no pixels here (a known limit). Writing follows DEC semantics exactly: only a set bit writes and a zero bit never changes a pixel, so colour passes overprint rather than erase. `P2=1` leaves unpainted pixels transparent; `P2` at its default 0 or at 2 initializes the canvas to the terminal's background (black here, since the core does not know the host theme) as it is created or grown.

**Bounds.** The canvas tracks its painted extent and its allocated capacity separately. Capacity grows geometrically — each side doubles until it covers what the next sixel needs — so a long run costs a handful of reallocations instead of one per column, and `finish` crops to the logical size. Capacity is never more than `MAX_IMAGE_SIDE` per side or `MAX_IMAGE_BYTES` of RGBA8; a sixel that would push past a cap paints nothing beyond it, later ones are ignored the same way, and `finish` returns the image as far as it fits — oversized is truncated, not refused. When doubling would bust the byte cap but the rectangle actually asked for still fits, that need is honored exactly (geometric overshoot never truncates a legal image) and the room left above the cap is split between both sides geometrically, so growth stays logarithmic in image size right up to the cap: `full_paint_near_cap_reallocates_logarithmically` measures 2 reallocs against a bound of 5, `staircase_toward_cap_reallocates_logarithmically` (a staircase that reaches the cap from just below, doubling one axis at a time) 13 against 40. All size math is saturating `u64`; a stream that paints nothing and declares no size answers `SixelError::Empty`. Bytes outside the commands above are ignored, parameter values saturate instead of overflowing, an unterminated introducer commits what it accumulated at the end of the stream, and a `!` repeat paints at most as many columns as can fit.

**Tests.** `src/graphics/sixel_tests.rs`: `decodes_reference_images` (`#[ignore]`, release: four reference images checked pixel for pixel against hand-decoded PNGs), `hls_colours`, `vt340_default_palette`, `repeat_and_newline`, `transparent_background`, `register_limit`, `unterminated_sixel_is_bounded`, `zero_size_is_error`, `header_only_allocates_nothing_before_finish`, `wide_growth_is_fast`, `near_cap_image_is_complete`, the two reallocation tests above, and `split_across_puts_is_identical` (a stream decodes identically whether it arrived whole or in arbitrary pieces).

### 14. OSC 1337 inline images (`src/graphics/inline.rs`)

`0.26.0+fbterm.8`, new. `InlineImageParser` is fed by change 10's inline-image callbacks: `inline_image_start(args)` with the bytes between `File=` and the first `:` (at most 4 KiB of them, and an abort can arrive with no start at all — a lone abort is a dropped image, not an unfinished one), `inline_image_put` → `put`, `inline_image_end` → `end`, `inline_image_abort` → `abort`. A sequence is `ESC ] 1337 ; File = <args> : <base64 payload>` ended by `BEL` or `ST`.

**Arguments.** `key=value` pairs separated by `;` — the parser keeps separators inside its argument text, so they are split here. The keys this terminal acts on are `size` (the payload's byte count, an advisory that refuses up front what the payload cap could not hold anyway), `width` and `height` (a cell count `N`, `Npx`, `N%` or `auto`, kept as `Dim` for the embedder to turn into a span), `preserveAspectRatio` (`0` stretches, `1` — the default — keeps the ratio) and `inline`. `name` is base64 and is read and dropped: nothing here shows a filename. Keys it does not act on (`format`, `inband`, …) are skipped, and a value that is not one of the defined forms leaves its key at its default — the protocol asks for unknown arguments to be ignored, there is no reply channel to complain through, and a default beats refusing an image over a detail. A key sent twice keeps its last value.

**Payload.** Base64 text (the vendored parser drops control characters inside an OSC string, so line breaks never arrive here) decoded incrementally by change 11: at most three characters carried between puts, a final group with or without padding, padding ending the payload whether more data follows it in the same put or in a later one — such a payload is not the base64 the protocol sends, so the image drops instead of being guessed at. Format and pixel size come from the header (the `imagesize` crate): PNG, JPEG and GIF, an animated file contributing its first frame; anything else is no image. A file cut short behind a readable header is still handed on — whether the encoded data was complete is the embedder's decode to report, not something the header can say.

**Display-only.** `inline=0` downloads the file without showing it, and a sequence that never says otherwise asks for the same thing; both are discarded and their payload streams past without being stored. An image is refused when a side passes `MAX_IMAGE_SIDE` or one RGBA8 frame of it would pass `MAX_IMAGE_BYTES`, and a payload past `MAX_PAYLOAD_BYTES` is dropped — a put whose decoded size would pass the cap is refused on its base64 length, before it becomes bytes. Every drop releases what it held at once, so no input can grow this parser past one payload cap. A sequence that carries no payload displays nothing.

### 15. Image placements, placeholders and virtual cells (`src/graphics/placements.rs`, `src/graphics/kitty_diacritics.rs`)

`0.26.0+fbterm.8`, new, plus anchor tracking in `src/grid/resize.rs`. `PlacementTable` is the terminal's bookkeeping of where images sit: one entry per display of a transmitted image, the invisible prototypes hosts draw with Unicode placeholders (virtual placements), and the few-byte `Placeholder` records that replace placements whose rows have scrolled out of view when scrollback images are not kept. It owns the ids clients use — kitty image ids and image numbers map to the `ImageKey`s the embedder sees — and reports every image it forgets exactly once with `Event::ImageReleased`.

**Stable lines.** A placement's row is `scrolled_lines + grid line` (change 2), which does not change while output scrolls it upward or the screen grows or shrinks. A rotation of the whole viewport — the only one that moves rows into history — therefore needs no placement updates at all: `GridWindow` carries the numbers that turn stable lines back into viewport rows when something asks what is visible. Sub-region rotations move content without touching the counter, so `after_scroll_up`/`after_scroll_down` shift the placements inside the rotated range and drop those whose content is destroyed.

**Room for an image.** Before a placement is laid out `Term` scrolls so its rows fit, exactly as the newlines it stands in for would: an image taller than the space below the cursor rotates the whole viewport — only for a full-screen scroll region; inside a partial one the display clips at the region's bottom edge instead — and the cursor rides up with its line, clamped to the region's top, so the anchor lands on the line its content actually ends up on rather than staying at the viewport bottom while its earlier rows scroll into history for nothing. The DECSDM-off sixel/inline rule wants the cursor one line *below* the image; when the image's last row is exactly the region's bottom — the usual case at a prompt — one more row scrolls so that line exists, as the newline this placement stands in for would (`sixel_at_the_bottom_of_the_screen_is_fully_visible`, `kitty_transmission_at_the_bottom_scrolls_its_text_up_with_it`). An image too tall for the screen keeps its old clamp: it ends on the bottom row, clipped below, and so does the cursor.

**Caps.** `MAX_PLACEMENTS` 4096 placements and as many virtual placements, `MAX_STORED_IMAGES` 512 images, `MAX_PENDING_DECODES` 64 transmissions awaiting a decode result, `MAX_PLACEHOLDERS` 100 000 placeholder records, and `MAX_IMAGE_SIDE` cells per axis for any requested span (a hostile request cannot ask for a span the terminal could not clamp to the screen). Overflow evicts the oldest by insertion stamp — an indexed operation, so eviction is O(log n), not a scan — releasing whatever stops being referenced. An image stays available while anything still references it: a placement, a virtual placement, an id or number map entry (a stored image a client can re-place without resending), or an in-flight decode. Kitty images therefore live until deleted, reset or evicted; sixel and inline images with no live placement are released as soon as their last one goes.

**Reflow.** A row-only resize needs nothing (stable lines survive it). A column resize moves each placement with its first cell, through the reflow exactly as the cursor follows content: `Term::resize` hands the placements' anchor cells to `Grid::resize_tracked`, which reports for each one where its cell went — the new `(line, column)` when it followed its row's content, or "cannot follow" with the line nearest where it used to sit when its cells were cut at the new width without reflow, its line was merged away, its content was destroyed by a height shrink, or its rows were evicted. `Term::resize` moves the placement in the first case and replaces it with its placeholder in the second, instead of dropping it silently; on the alternate grid, whose row passes have no scroll observer, anchors keep their cells through the row passes and are shifted to their new absolute lines afterwards — and that screen's anchor list is re-read *after* the shifts, each outcome paired with the record its placement became by insertion stamp (the one identity a shift keeps), so `apply_reflow` moves current records rather than pairing outcomes with pre-shift copies. `move_placement` leaves a record it cannot find at the line it was given alone — a missing record is a desync, not a reason to insert another copy — and the live-placement count decrements saturate with a debug assertion, as reference counts do, so no desync can wrap it. Placeholder line anchors inside a reflowed region are not tracked (they are host-drawn text, not content), so after a column resize they stay on their old stable lines; only the cap and the width prune touch them. `resize_tracked` replays the reflow's own decisions in step with the loop (`AnchorTracker`, `src/grid/resize.rs`): when merging an upstream that changes `grow_columns` or `shrink_columns`, keep the tracker in step with what the loop actually moves, and re-run `resize_reflow_moves_placement_with_its_first_cell`, `resize_unfollowable_anchor_becomes_a_placeholder`, `cursor_position_image_follows_reflow_across_resizes` and `cut_column_placeholder_sits_on_anchors_row`.

**Virtual placements (`U=1`).** A virtual placement has no pixels of its own: a host displays it by printing the private-use character `PLACEHOLDER_CHAR` (U+10EEEE) with combining diacritics encoding the cell's row and column within the placement, and a foreground color encoding the image id. `ROW_COLUMN_DIACRITICS` is the protocol's `rowcolumn-diacritics.txt` verbatim (297 entries, sorted, so `diacritic_index` binary-searches it); `decode_placeholder_cell` decodes one cell to `(image id, row, column)` — the id's low 24 bits from a truecolor foreground or an indexed palette index (a named color encodes no id), two marks giving row and column and a third adding the most significant id byte (it must itself be a byte value). A cell with fewer than two marks inherits them from the placeholder cell to its left per the protocol, which a stateless single-cell decode cannot see, so those cells decode to `None` and hosts apply the inheritance rules themselves; `Term::kitty_virtual_image(image_id, placement_id)` then resolves the decoded ids to the stored image's key and the virtual placement's cell span.

### 16. Image events, the embedder's image API and capability replies (`src/event.rs`, `src/term/mod.rs`)

`0.26.0+fbterm.8`. The terminal owns the protocol state (changes 12 to 15) and hands pixels to the host; the host owns decoding the container formats and drawing.

**Events.** `Event::ImageReceived { key, data }` delivers one image's payload: `ImageData::Rgba { width, height, pixels }` for pixels the terminal decoded itself (sixel output, raw kitty RGB/RGBA — straight, non-premultiplied 8-bit RGBA, `pixels.len() == width * height * 4`) or `ImageData::Encoded { format, bytes, width, height }` for a container format (`ImageFormat::Png`, `Jpeg`, `Gif`) with the dimensions its header declares, so placements can be laid out before decoding finishes. `Event::ImageReleased(ImageKey)` says nothing references that image any more and the embedder should free it: sent exactly once per key, when its last placement, placeholder or stored reference is gone, and a released key is never reused. `ImageKey(pub u64)` is handed out in increasing order by `Term`.

**Reporting back.** `Term::image_decoded(key, result)` reports the host's decode result for an `Encoded` payload: it sends the kitty reply that was waiting on it (`OK`, `EBADPNG` or `ENOMEM`) and, on failure, removes the image and its placements. Call it for every `ImageReceived` carrying `Encoded`; `Rgba` payloads were decoded by the terminal already. `Term::tick(now)` runs the stall watchdog of change 12; hosts call it periodically or after feeding bytes.

**Switches.** `Term::set_images_enabled(on)` (on by default) is the host's setting, not the program's: neither `RIS` nor `set_options` changes it. On, the terminal behaves like one with graphics support. Off, every image sequence is consumed and discarded, no payload reaches the embedder, no placement is made, the kitty support query answers `ENOTSUPPORTED` and every other completed frame does too (subject to its quiet level), XTSMGRAPHICS requests answer with an error status and DA1 leaves out the sixel bit; switching off also drops everything stored or displayed — each image released exactly once — and a decode result that arrives afterwards answers nothing. `Term::set_scrollback_images(keep)` (off by default) decides whether a placement whose rows have all left the viewport becomes a placeholder line (`[image 640×480]`, see `Term::visible_placeholders`) and releases its image, or is kept so it scrolls back into view; with keeping on, `Term::evict_oldest_scrollback_image()` lets the host reclaim memory from the oldest one when it is over its own cap. `Term::set_cell_pixel_size(width, height)` (each axis clamped to at least 1) is what placements convert pixel sizes to cell spans with; hosts that know their font metrics should set it before images arrive.

**Drawing.** `Term::visible_placements()` returns the placements intersecting the current view with `row_in_view` counted from the top of the view (negative when the placement starts above it), in the order to draw them (`z` orders overlapping images; negative draws under text). `Term::visible_placeholders()` returns the placeholder lines in view as ready text. `Term::kitty_virtual_image(image_id, placement_id)` resolves a decoded placeholder cell (change 15) to its image and span.

**Capability replies.** With image support on: DA1 answers `\x1b[?62;4;22c` (VT500-class conformance plus the sixel graphics bit and ANSI colour), XTSMGRAPHICS (`CSI ? Pi ; Pa ; Pv S`) reports item 1 as the sixel colour-register count (1024) and item 2 as the text area in physical pixels capped at `MAX_IMAGE_SIDE` per axis, and since both are fixed capabilities, read, read-maximum, set and reset all answer success with what stands — nothing is adopted from `Pv`, because reporting a number the terminal did not take would claim a capability it does not have. An unknown item answers status 1 (error in `Pi`), an unknown action status 2 (error in `Pa`); with image support off every request answers status 1 without a value. `CSI 14 t` and `CSI 16 t` are answered from the stored cell size once `set_cell_pixel_size` has run, so image programs sizing their output by it see the same numbers placements do; until then the host is asked through `Event::TextAreaSizeRequest`, as `CSI 14 t` always was.

**Events during a resize.** Placement events generated by a resize are parked (`resize` has no listener bound) and flushed by the next bounded operation: printable input, the start of a graphics sequence, `image_decoded`, or `tick`. Control-only output — what a program might answer a resize with (`DECRQM`, cursor moves, `ED`) — does not flush them, so an idle terminal gets its deferred releases from the host's periodic `tick` rather than from the next printable character.

**Tests.** `src/term/mod.rs`: the `image_support` module (`da1_advertises_sixel_when_on`, `xtsmgraphics_replies`, `disabled_images_are_inert`) and the protocol tests named in changes 12 to 15, which run through a real `Term` with a recording listener.

**Merging.** Nothing upstream corresponds to this. Upstream changes to `identify_terminal` (DA1), the `CSI 14 t`/`16 t` handlers or `Handler`'s method set need the graphics replies carried along; new `Event` variants are additive for listeners but change what a host must handle.

## Graphics

What a host has to do to display images, and the numbers it can rely on. The terminal parses the protocols; the host decodes PNG/JPEG/GIF and draws.

```text
bytes ──▶ Term (parser + graphics state) ──▶ Event::ImageReceived { key, data }
                                              │  Rgba: draw as is
                                              │  Encoded: decode, then
                                              ▼
                            Term::image_decoded(key, Ok | Err(Corrupt|TooLarge))
                                              │  answers the client (OK / EBADPNG / ENOMEM)
                                              ▼
              Term::visible_placements() / visible_placeholders() ──▶ draw
                                              │
                                              ▼
      Event::ImageReleased(key) ──▶ host frees its decoded copy (once, per key)
```

1. **Set the geometry first.** `set_cell_pixel_size(w, h)` with the real font metrics; spans, `CSI 14 t`/`CSI 16 t` and XTSMGRAPHICS all answer from it. Without it a pixel-sized image still gets a span (the default is 1×1), but one computed against cells of one pixel.
2. **Decide the host policy.** `set_images_enabled(bool)` (on by default; off discards everything, see change 16) and `set_scrollback_images(bool)` (off by default: scrolled-off images become `[image WxH]` placeholder text and free their pixels).
3. **Answer decode requests.** On every `Event::ImageReceived` carrying `ImageData::Encoded`, decode the bytes (or refuse them) and call `Term::image_decoded(key, result)` — that is what answers a kitty client waiting for its transmission reply. A `Rgba` payload needs no answer: the terminal decoded it.
4. **Draw from the view.** `visible_placements()` in the order returned (it is already paint order; `z < 0` belongs under the text), cropping to each entry's `src` rectangle and offsetting by `x_off`/`y_off`; `visible_placeholders()` as text; for kitty virtual placements, decode placeholder cells with `kitty_diacritics::decode_placeholder_cell` and resolve them with `Term::kitty_virtual_image`.
5. **Free on release.** `Event::ImageReleased(key)` arrives exactly once per key, when the last thing referencing it is gone. While the host keeps images in scrollback past its own cap, `evict_oldest_scrollback_image()` turns the oldest into a placeholder and releases it outright.
6. **Run the watchdog.** Call `Term::tick(now)` periodically (or after feeding bytes); it drops a chunked kitty transmission that stopped mid-upload ten seconds ago (`STALL`), answers it `ENOMEM`, and delivers any image events a resize parked — releases stay queued through control-only output, and `tick` is what covers an idle terminal.

**Limits, with values.** A remote stream cannot make this grow past these numbers; each is a constant in the crate:

| Limit | Value | Where |
| --- | --- | --- |
| `vte::MAX_OSC_BYTES` | 64 KiB | one buffered OSC string (change 10) |
| streamed OSC 1337 arguments | 4 KiB (`MAX_OSC_STREAM_ARGS`) | over the cap: abort with no start dispatched |
| parser parameters | 32 (`MAX_PARAMS`), OSC parameters 16 | joined into the last one past the cap |
| `graphics::limits::MAX_IMAGE_SIDE` | 10 000 px per axis | declared or measured image side; also the span cap in cells |
| `graphics::limits::MAX_IMAGE_BYTES` | 64 MiB | one RGBA8 frame: sixel canvas, inflated kitty data, what an `Encoded` decode is expected to fit |
| `graphics::limits::MAX_PAYLOAD_BYTES` | 16 MiB | decoded payload of one transmission or file (base64 text is capped by its own length before decoding) |
| `graphics::limits::STALL` | 10 s | without progress a chunked kitty transmission is dropped with `ENOMEM` |
| sixel colour registers | 1024 per image (`REGISTERS`) | what XTSMGRAPHICS item 1 reports |
| `graphics::placements::MAX_PLACEMENTS` | 4 096 | placements, and as many virtual placements |
| `graphics::placements::MAX_STORED_IMAGES` | 512 | images kept for re-placing without resending |
| `graphics::placements::MAX_PENDING_DECODES` | 64 | transmissions awaiting a decode result |
| `graphics::placements::MAX_PLACEHOLDERS` | 100 000 | `[image WxH]` records kept for scrolled-off images |

**What is not supported here, and what answers instead.** File-based kitty media (`t=f`, `t=t`) — `EBADF`, this fork never reads local files; indexed kitty formats `f=8`/`f=16` and kitty animations (`a=f`, `a=a`, `a=c`) — `ENOTSUPPORTED`; OSC 1337 downloads that do not ask for display are discarded silently (there is no reply channel in that protocol); a sixel's aspect parameters change nothing about its pixels.

### Fuzzing

`fuzz/` is its own cargo workspace (`[workspace] members = ["."]`, its own `Cargo.lock`, and `target/`, `artifacts/` and `corpus/` ignored), so the gates above do not build it and libfuzzer's dependency tree stays out of the crate's. Four targets take plain bytes (no `arbitrary`-derived input): `kitty`, `sixel` and `inline` drive one protocol state machine over hand-rolled framing that varies chunk sizes, terminator form, aborts and decode replies; `parser_strings` feeds arbitrary terminal bytes through the parser into a real `Term` and then does what a host does between reads — answers decode results for the keys its listener kept, runs `tick` on a moving clock, resizes (widths start at 2 columns: shrinking to a single column while a wide character sits where the cut lands loops in the reflow, which is upstream's behavior and its own change to make), switches to the alternate screen and back, toggles scrollback images and evicts one — and reads the view back through `visible_placements`, `visible_placeholders` and `decode_placeholder_cell`. Each target's module docs say how its framing works.

Seeds under `fuzz/seeds/<target>/` pin the shapes that reviewers reported or that the caps turn on: a huge requested cell span, a bare `ESC` inside an APC, `ESC ESC \`, a bare `ESC` at the end of a read, base64 padding split across chunks, and a sixel staircase that reaches the capacity cap from just below. They are committed and run before generated input.

Run from the repository root (cargo-fuzz takes corpus paths relative to the working directory):

```sh
cargo +nightly install cargo-fuzz   # once
(cd fuzz && cargo +nightly check)   # the targets compile; not part of the gates above
mkdir -p fuzz/corpus/kitty fuzz/corpus/parser_strings
cargo +nightly fuzz run kitty fuzz/corpus/kitty fuzz/seeds/kitty -- -max_total_time=60
cargo +nightly fuzz run parser_strings fuzz/corpus/parser_strings fuzz/seeds/parser_strings -- -max_total_time=60
```

`.github/workflows/fuzz.yml` runs every target on a nightly toolchain: 60 s per target on pull requests touching the parsers, weekly with the corpus cached between runs and minimized afterwards, and on a manual run for as long as asked. A failing input is uploaded as an artifact. It is a separate workflow from `ci.yml` because it needs the nightly toolchain plus `cargo-fuzz`, which the gates do not.

### The differential test's oracle

`tests/differential.rs` compares feathercritty with 0.26.0 on generated byte streams. Since `0.26.0+fbterm.4` the comparison crate is the vendored, patched 0.26.0 source in `tests/oracle/`, a path dev-dependency named `alacritty_terminal`, instead of the crates.io release:
- The oracle is the published 0.26.0 `src/`, `Cargo.toml` and `LICENSE-APACHE` plus exactly the patches listed in `tests/oracle/PATCHES.md` (the `occ` fix and the "no row" reads of change 6; changes 1 and 5 are modeled by the harness, not patched).
- `tests/oracle_pristine.rs` checks it offline: it applies `PATCHES.diff` in reverse and compares SHA-256 values with `MANIFEST`, so the vendored files are provably 0.26.0 plus the patches.
- Vendored files are exempt from the fork notice line (unmodified ones are byte-identical to upstream; patched ones carry a "Patched by the featherbit authors" line). `PATCHES.diff` and `MANIFEST` are data and carry none.
- To move the oracle to a new upstream release, follow "Moving to a new upstream release" in `tests/oracle/PATCHES.md` and "Moving the oracle to a newer upstream release" in `tests/support/mod.rs`.

## Updating from upstream

The `upstream` branch and the release base are produced with `git subtree split`, which is deterministic: the same upstream commits always give the same split commits (author and committer data are copied from the originals), so a later split of newer upstream history extends the existing `upstream` branch and shares its commits. The current split was made with git 2.54.0 from upstream `master` at `542147067dd016fc5f49120ef0ba605a98a4e3a7` (split tip `17d568a11bc2161304a0e12d321d1e54f5d5afe6`).

1. Split the upstream history (from a fresh or updated clone; only reading from upstream):

   ```sh
   git clone https://github.com/alacritty/alacritty.git
   cd alacritty
   git subtree split --prefix=alacritty_terminal origin/master
   # For a release, split its tag too (release commits usually live on a release branch):
   git subtree split --prefix=alacritty_terminal alacritty_terminal_vX.Y.Z
   ```

   Each command prints the tip of the split history.

2. Bring it into feathercritty and fast-forward `upstream` (the update must be a fast-forward; if it is not, the split was not reproduced, so check the git version and the command):

   ```sh
   cd ../feathercritty
   git fetch ../alacritty <master split sha>:refs/heads/upstream
   git fetch ../alacritty <release split sha> && git tag alacritty_terminal_vX.Y.Z <release split sha>
   git push origin upstream alacritty_terminal_vX.Y.Z
   ```

3. Adopt upstream changes on `main` by merging, never by rebasing: featherbit terminal pins commits of `main`, and they must stay reachable.

   - A single upstream fix: `git cherry-pick -x <sha from upstream>`.
   - A new release: `git merge alacritty_terminal_vX.Y.Z`, resolve conflicts (usually `Cargo.toml` and `Cargo.lock`), drop changes that upstream now carries, set the version to `X.Y.Z+fbterm.1`, re-vendor the oracle, and update the change list above.

4. Run the checks under [Development](#development), push `main`, and bump the `rev` in featherbit terminal.
