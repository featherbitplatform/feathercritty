# feathercritty

feathercritty is the terminal emulation library used by [featherbit terminal](https://github.com/featherbitplatform/terminal): the VT parser handler, the grid with its scrollback, selection, search and the PTY event loop. It is a fork of `alacritty_terminal` 0.26.0 with a few small changes, listed below.

The crate is not published on crates.io. Use it as a git dependency pinned to a commit:

```toml
[dependencies]
feathercritty = { git = "https://github.com/featherbitplatform/feathercritty", rev = "<full commit sha>" }
```

## Origin

The repository holds the history of the `alacritty_terminal/` directory of [alacritty/alacritty](https://github.com/alacritty/alacritty), extracted with `git subtree split` (see [Updating from upstream](#updating-from-upstream)):

- `upstream` is the extracted history of upstream `master`, unchanged.
- `main` starts at the `alacritty_terminal_v0.26.0` release (tag `alacritty_terminal_v0.26.0` here, commit `a6b23e80c7fe4e416e96a39b34cb300fa9db3aca`; the release commit lives on upstream's `v0.17` branch, so it is not on `upstream`) and adds the changes below as separate commits.

## Why this fork exists

feathercritty is a fork of [`alacritty_terminal`](https://github.com/alacritty/alacritty/tree/master/alacritty_terminal), the terminal emulation library of the Alacritty project, maintained for [featherbit terminal](https://github.com/featherbitplatform/terminal).

featherbit terminal is developed with the help of AI coding tools. The Alacritty project does not accept contributions that include content generated by large language models ([CONTRIBUTING.md](https://github.com/alacritty/alacritty/blob/master/CONTRIBUTING.md)), and we respect that choice. Rather than send such changes upstream, we keep them here, so featherbit terminal can keep moving forward (for example on scrollback memory use) without asking the Alacritty maintainers to review or carry them.

This fork is not affiliated with or endorsed by the Alacritty project. Please do not report issues with this fork to Alacritty; open them here instead. All credit for the original work goes to the Alacritty authors.

## Changes from alacritty_terminal 0.26.0

Files changed by this fork start with the line `// Modified by the featherbit authors for feathercritty; see README.md for the list of changes.` (`#` in `Cargo.toml`).

### 1. Keyboard mode stack eviction (crash fix, upstream commit)

`src/term/mod.rs`, `Term::push_keyboard_mode`. When the kitty keyboard protocol's flag stack is full (`KEYBOARD_MODE_STACK_MAX_DEPTH`, 4096), 0.26.0 evicts the oldest entry from the wrong stack:

```rust
// before
let removed = self.title_stack.remove(0);
// after
let removed = self.keyboard_mode_stack.remove(0);
```

With an empty title stack the original line panics (`Vec::remove(0)` on an empty vector), so any program or remote host that sends `CSI > flags u` 4097 times crashes the terminal's parser while the protocol is enabled. This is upstream's own fix ("Fix Kitty keyboard mode stack size limit", made after 0.26.0), cherry-picked from `upstream` with its original authorship.

### 2. Scroll counter on the grid (scrollback search)

`src/grid/mod.rs`: `Grid` gains a `scrolled_lines: i64` field (skipped by serde), incremented by `positions` where `Grid::scroll_up` rotates the whole buffer into history, and a getter `Grid::scrolled_lines()`. `src/grid/resize.rs`: `grow_lines` subtracts the lines it adds (lines pulled back from history move down the screen, and the rotation its `scroll_up` counts only undoes the growth), so the counter can go below zero (wrapping arithmetic). `scrolled_lines() + line` is a line number that stays the same while output scrolls the line upward and while the screen grows or shrinks, which featherbit terminal's find bar uses to keep its matches and current match in place as new output arrives. Nothing in the library reads the field.

### 3. Inactive grid getter (tab export)

`src/term/mod.rs`: `Term::inactive_grid()` returns the grid that is not shown (the normal screen and its scrollback while the alternate screen is active). featherbit terminal's tab export writes the normal screen's history even while a full-screen program (vim, less, top) has the alternate screen up. Read-only; nothing else changes.

### 4. Packaging

- The package is named `feathercritty`; the doc test and `tests/ref.rs` use the new name. Authors and license are unchanged; `repository` and `homepage` point here, and `publish = false` keeps the crate off crates.io.
- Version scheme: `<alacritty_terminal version>+fbterm.<n>`, currently `0.26.0+fbterm.5`. The build metadata (`+fbterm.n`) counts this fork's revisions on top of one upstream release and starts again at 1 when `main` moves to a new upstream release. Cargo ignores build metadata when comparing versions, which does not matter for a git dependency pinned by `rev`.
- The manifest no longer inherits `edition` and `rust-version` from the Alacritty workspace (both set to the workspace's values, 2024 and 1.85.0), and `readme` points to this file.
- `LICENSE-APACHE` is a copy of the upstream file instead of a symlink into the Alacritty workspace. The Alacritty workspace's `rustfmt.toml` (nightly options) and the `Cargo.lock` shipped with the published 0.26.0 crate are included so the crate formats and builds on its own.
- `src/lib.rs` allows `clippy::question_mark`: clippy releases newer than the upstream code flag three matches in `src/tty/unix.rs`, and the crate denies `clippy::all`. Allowing the lint keeps the upstream code unchanged.
- The reference test data in `tests/ref` (about 46 MB on disk) is kept. The whole repository history packs to about 1 MiB, so fetching it as a git dependency stays cheap.

### 5. Regex search over wrapped wide characters (hang fix)

`src/term/search.rs`: `Term::search_next`, `Term::next_match_right`, `Term::next_match_left`, `Term::regex_search_internal`, `RegexIter` (`new`, `next`, the cycle-check fields and `bound_fired`), `LazyDfa` (one field), and new items `Term::final_match`, `Term::last_in_range_before_repeat`, `Term::match_in_range`, `Term::glyph_cells`, `Term::glyph_end`, `Term::expand_wide_underflows`, `Term::search_distance`, `RegexSearch::take_bound_fired` and `LoopState`. `0.26.0+fbterm.2` to `+fbterm.4` fixed the hangs by changing how the iteration stops and cutting matches to the range; that changed answers 0.26.0 gives inside the range and produced "matches" whose text the pattern does not match. `0.26.0+fbterm.5` replaces it with the rules below.

**The trigger** is a leading spacer next to the end of a search. With a wrapped wide character after it (the wide character at column 0 of the next line, its spacer at column 1), searches step over the character two or three cells at a time: left from its spacer to the leading spacer, right from the leading spacer to its spacer. With a stale leading spacer, one whose next line does not start with a wide character (a resize or an erase leaves it behind, sometimes in the middle of a line), a rightward step still reads the next cell in its place and steps over the cell after it. 0.26.0 checks for its end only on the cells where a step lands, so:
- `regex_search_internal` can step over its end and read around the buffer; when the text gives it no match, forever. That hung leftward `search_next` with `max_lines` (its end is column 0 of any line), the empty pattern, and searches from a cell to itself;
- `RegexIter` stops only when a match ends exactly on its end. A match covering the end, or ending behind its origin next to a stale spacer, sends it back to an origin it already searched from, and it cycles through the same matches forever, so `search_next` never returns; this hung unbounded searches too, the find bar's ordinary case;
- matches can lie outside the searched range: the reading runs past the end, or a search from a cell to itself reads a full lap.

**The rules now:**
1. **The iteration is 0.26.0's.** `regex_search_internal`, `regex_search_left`/`right`, `RegexIter` and the choice in `search_next` (the first match past the origin, else the first match) run 0.26.0's code: same starts, stops, steps, second searches and continuation. `RegexIter` yields exactly 0.26.0's matches, out-of-range ones and repeats included.
2. **Bounds only where 0.26.0 would never end.** Both are exact cycle checks (Brent's algorithm, constant memory), so they fire only where 0.26.0 provably repeats itself forever, and nowhere else:
   - `regex_search_internal`: each time the search wraps around the buffer it records everything its further course depends on (`LoopState`: position, DFA state, bytes consumed so far up to 3, the match so far, the line-wrap flag, the DFA cache's clear count); when that repeats, so would every later lap. The search then returns no match.
   - `RegexIter`: each step depends only on its origin, so an origin it already searched from means it repeats forever. The iteration then ends.
   Either way `RegexIter::bound_fired` is set.
3. **Only the final answer of `search_next` changes, and only when 0.26.0 has none in range.** When the iteration hit a bound (0.26.0 never returns, or panics: rule 5), or 0.26.0's answer lies outside the searched range, `search_next` returns the last match inside the range that the iteration produced, or `None`. An iteration that 0.26.0 repeats forever counts up to its first repeated match (found with the second half of Brent's algorithm by re-running the iteration; the origins can start repeating one step later), so the answer does not depend on when the check noticed the repeat. An iteration whose last search starts at the range's end ends there even if that search repeats an earlier match; 0.26.0 terminates, and its answer stands. Every match returned is one the regex matched, unchanged.
   - **In range** (`match_in_range`; the differential test classifies 0.26.0's answers with the same rules): unbounded searches cover the whole buffer. A bounded one runs from its start to its end in its direction, wrapping around the buffer like the search. The match's far end may also lie in the cells read together with the character at the end (`glyph_cells`: right, the two cells after a leading spacer or the spacer after a wide character; left, the wide character of a spacer and a leading spacer before a wrapped wide character), its near end in those read with the character at the start in the other direction, and its near end must not come after its far end along the range (a match with both ends in the range in the wrong order ran around the whole buffer).
4. **`search_next`'s origin stays in the grid.** Going right, `search_next` moves its origin to the end of the character there (`expand_wide`), which for a leading spacer is column 1 of the next line. On the bottommost line (a stale spacer) there is no next line: 0.26.0 panics in debug builds and reads whatever row its ring holds there in release builds. The origin is then the cell the search lands on after reading the spacer (`glyph_end`), on the same line. 0.26.0 has no defined answer there.
5. **No panic going left from a stale spacer at column 0.** Going left, `expand_wide` moves from a wide char spacer one column back to its wide char. A stale spacer at column 0 (a resize to 2 columns and an erase leave one behind) has no column before it: 0.26.0 subtracts from column 0, which panics in debug builds and goes on from a wrapped-around column in release builds. It does so for `search_next`'s origin, and in `RegexIter` when a leftward match ends on such a spacer and the origin moves past it. Both builds now stop where the debug build panics (`Term::expand_wide_underflows`): `search_next` from such an origin answers `None`, and `RegexIter` ends before yielding that match, with `bound_fired` set, so `search_next` answers with the last in-range match yielded before it (rule 3), or `None`.

**Where answers differ from 0.26.0:** only where 0.26.0 never returns, panics or reads outside the grid (rules 2, 4 and 5), or answers with a match outside the searched range (rule 3). Wherever 0.26.0 terminates with an in-range answer, the answer is 0.26.0's (a debug build of 0.26.0: under rule 5 a release build goes on from a wrapped-around column and can answer in range where the fork, like the debug build, stops). `RegexIter` differs only by ending where 0.26.0's would repeat forever or panics.

**Costs and termination.** Neither bound is reached where 0.26.0 terminates. A search that 0.26.0 would never finish runs until its recorded state has gone round once, about twice the state's period in laps of the buffer, and that period follows the pattern: a counted pattern over long wrapped lines keeps the DFA alive with a counter (up to about 1,000 states fit the DFA cache), so `(?:[ab中]{997})*b` over a 20,000-line buffer of wrapped 100-column lines took 37 s before the check fired, about 3 minutes extrapolated to 100,000 lines, and `search_next` can run several such searches plus the reruns of rule 3. 0.26.0 never finishes there at all. A search can also end because the DFA cache gives up ("Regex exceeded complexity limit" in the log, and no match), as in 0.26.0. That give-up is also what makes the loop check exact and finite: the search never reports progress to regex-automata's cache, so the cache counts as inefficient and gives up on its fourth clear (`minimum_cache_clear_count(3)` and `minimum_bytes_per_state(10)` in `RegexSearch::new`, regex-automata 0.4.11), which caps the clears at 3 and keeps the recorded state finite. `cache_give_up_ends_a_search` pins it under a timeout. An iteration that 0.26.0 repeats forever runs about one to three times its cycle before the check notices it, and the answer then re-runs it up to twice.

- Tests: `wrapped_wide_*`, `empty_pattern_terminates`, `stale_leading_spacer_*`, `stale_spacer_*`, `range_ending_on_*`, `search_origin_on_bottom_line_stale_spacer`, `stale_spacer_column_zero_*`, `repeat_from_range_end_ends_iteration`, `left_match_past_range_start_wrapping`, `left_iteration_stops_where_upstream_stops`, `regex_iter_ends_where_upstream_repeats`, `rereview_*`, `counted_pattern_hits_the_cycle_check` and `cache_give_up_ends_a_search` in `src/term/search.rs`, with timeouts so a regression fails instead of hanging. Their expected values are 0.26.0's, recorded from the differential test's oracle, where 0.26.0 answers in range; `RegexIter` tests check 0.26.0's endless sequence up to the bound. `wrapped_wide_fuzz` runs every search over 2- to 4-column grids with wrapped and stale leading spacers, with and without scrollback, and checks that all of them end and that `search_next` answers inside its range. In `tests/differential.rs`, `search_soak_regressions` replays the soak seeds and `search_grid_probe` compares `search_next` with 0.26.0 on hand-built small grids written into both crates. Where 0.26.0 has no in-range answer, the differential test walks 0.26.0's own iteration up to its first repeated match, its end or its panic (rule 5, treated as a panic in release builds too), and requires feathercritty's answer to equal the one rules 3 and 5 pick from that walk (`check_search_walked`, `Walk::answer`). `search_grid_probe` writes stale spacers at any column, so it reaches rule 5.
- When merging upstream: if `regex_search_internal`, `skip_fullwidth`, `RegexIter` or `next_match_left`/`right` changed, keep this change's additions (the loop check and `LoopState`, the iterator's cycle check and its stop at `expand_wide_underflows`, `final_match`) in step with what the code reads and chooses; if upstream's `expand_wide` stops subtracting from column 0, drop rule 5 and the differential test's matching workaround in `search_terminates`; the `// feathercritty:` comments name each. If upstream bounds its loops and keeps answers in range itself, drop this change, re-run the tests above and the differential test. Re-check termination (run `cache_give_up_ends_a_search` and `counted_pattern_hits_the_cycle_check`) on a regex-automata update, if `RegexSearch::new` changes the cache config, or if upstream starts reporting search progress to the cache (`Cache::search_start`/`search_update`): the loop check relies on the cache giving up on its fourth clear.
- Not changed (0.26.0 behavior, so the differential test compares it):
  - On 2-column grids, the right step from column 0 over a leading spacer to column 1 also looks like a line break to `regex_search_internal`'s line-break check, which resets the match.
  - A stale leading spacer reads differently by direction: going right, the search reads the next cell in its place and skips the cell after that; going left, it reads a blank. The two searches of one match can then disagree; the match fails or ends past its origin.
  - The line-break check compares the cells the search lands on, after the fullwidth skip. A line that ends in a wide character's spacer without wrapping, followed by a line that starts with a wide character, therefore reads as one line, and a match can span the two lines (differential soak seed `realistic_cjk` 1000223).
  - When the bottom line wraps (its last cell has `WRAPLINE`), the search reads on from it into the top line, so a match can run around the buffer's end and start after its end in grid order (differential soak seed `random_streams` 1000017).

### 6. Screen and history split (explicit history reads)

`0.26.0+fbterm.4`. Phase 1 of the compact scrollback work: the grid keeps the visible screen and the scrollback in two containers, and every read of scrollback goes through an explicit API. The scrollback is still dense (a `VecDeque` of `Row`s) in this release, so memory use and speed are about what 0.26.0 had (ingest within about 4%, one alternate-screen row 1.7% slower; see the benchmark note below and `benches/RESULTS.md`); the point is the API, which lets a later release store history compactly without changing callers.

**API**
- `Grid<T>` is `{ screen: Screen<T>, history: History<T> }`. `Grid::screen()` and `Grid::screen_mut()` return the screen, a handle over upstream's `Storage` ring that implements `Index`/`IndexMut` for `Line` and `Point` with upstream's `debug_assert!` range checks. The `max_scroll_limit` field is now `history.limit()`.
- **`Grid` itself no longer implements `Index`/`IndexMut`.** Indexing is screen-only (`grid.screen()[line]`, lines `0..screen_lines`). History lines (negative `Line`) are read through:
  - `RowReader<T>`: `RowReader::new()` and `reader.row(&grid, line) -> &Row<T>` for a whole row of screen or history. Keep one reader and reuse it; a later release decodes history rows into its scratch row.
  - `Grid::cell(point) -> T` (an owned cell), `Grid::wraps(line) -> bool` and `Grid::is_clear(line) -> bool`, for single reads that work for screen and history lines.
- `GridIterator` yields `Indexed<T>` by value (it used to borrow `&T` from the grid). `GridIterator::cell(&self) -> &T` borrows the current cell without cloning; `advance`/`retreat` (`pub(crate)`) step without producing an item.
- `History<T>` (`src/grid/history.rs`, new) owns the scrollback: `new`, `len`, `is_empty`, `limit`, `set_limit`, `push_newest(&Row)`, `pop_newest`, `pop_oldest`, `read`, `update`, `wraps`, `is_clear`, `clear`. Cells stored in it implement the public `HistoryCell` trait, defined in `src/grid/compact.rs` with the row codec (change 7).
- The only write to history outside scrolling and resizing is the one in `Term::input` (`Grid::update_history_row`).
- (Phase 1 only: `History::push_newest_recycle` swapped the departing screen row for a recycled one in `scroll_up`. Change 7 replaced it with `push_newest` plus the in-place reset upstream does.)
- serde form is unchanged: the same fields as upstream (`raw.inner` from the bottom line up, `zero` 0, `len`, `visible_lines`, the scroll limit), through private proxy structs. Deserialization splits at the grid's `lines`, because old reference files carry a stale `visible_lines`. `tests/ref/` data is unchanged.

**Merging a new upstream release.** Upstream code that indexes the grid (`self.grid[point]`, `grid[line]`, `grid.raw`-style access) will not compile after a merge. Classify each site:
- *Screen*: the line is always `0..screen_lines` (handler writes, cursor, the visible region). Use `grid.screen()` / `grid.screen_mut()`.
- *History-capable*: the line can be negative (selection text, search, vi motions, anything that follows a point or a neighbouring line). Use `Grid::cell`, `Grid::wraps`, `Grid::is_clear`, a `RowReader`, or `GridIterator`.

The sites classified as history-capable in 0.26.0: `Term::line_to_string`, `Term::expand_wide`, the vi cursor in `RenderableCursor`, in `search.rs` `regex_search_internal`, `glyph_cells`, `skip_fullwidth`, `bracket_search`, `inline_search_right`, `line_search_left`/`line_search_right`, in `vi_mode.rs` `ParagraphUp`/`ParagraphDown` and `semantic` (`expand_semantic`, `is_space`, `is_wrap`), and every `GridIterator` user (`display_iter`, `clear_viewport`, the regex, bracket, semantic and inline searches). Everything else is screen.

**Behavior changes made with it** (both are also patched into the differential test's oracle, see Development)
1. *`Row` `occ` invariant* (`src/grid/row.rs`, `Row::grow` and `Row::append`). Upstream documents that all cells after `occ` are equal, and `Row::reset` relies on it, but `grow` padded with default cells without raising `occ`, and `append` did `occ += n` even when `occ` was below the old length. A reset could then leave stale cells behind, and what a recycled row looked like depended on which physical row the ring had recycled.
   - Before: `grow` left `occ` alone; `append` set `occ += vec.len()`.
   - After: `grow` first sets `occ = max(occ, len)`; `append` sets `occ = len + vec.len()` when `vec` is not empty.
2. *Reads outside the grid are "no row"*. 0.26.0 read lines just outside `topmost_line()..=bottommost_line()` in a few places: debug builds failed a `debug_assert!`, release builds read whichever row the ring held there (a cache row or a wrapped-around screen row).
   - `Term::line_to_string`. Before: a selected line ending in a leading wide-char spacer appended `grid[line - 1][Column(0)].c`, even on the topmost line. After: it adds nothing above the topmost line.
   - Vi motions. Before: the cursor could leave the grid (`Middle` on a one-line screen without history, `Right`/`Last` across a wrap or leading spacer on the bottom line). After: `ViModeCursor::motion` clamps the point into the grid (`grid_clamp(term, Boundary::Grid)`).
   - Iterators and readers. Before: undefined (see above). After: `Grid::cell` and `GridIterator::cell` return a default cell, `Grid::wraps` returns false, `Grid::is_clear` returns true. `RowReader::row` and the `History` methods keep a `debug_assert!` (a caller bug) and in release return default cells of the grid's width, a no-op, false and true.

**Other changes**
- `Storage::initialize` grows by exactly the rows needed (upstream added at least 1000 at a time, a history cache); it keeps upstream's hidden rows beyond `len`, which `scroll_up` recycles. (Phase 1 also had a small spare-row pool there; change 7 removed it, the history's block pool does that job.)
- `Grid` equality compares content, including history.
- `Grid::scroll_up` moves the departing rows into history, then rotates and resets as upstream did.
- `resize.rs`: `grow_lines` moves popped history rows onto the new top rows and removes only the rows `scroll_up` pushed; it clamps the display offset unconditionally (upstream's `decrease_scroll_limit` always clamped). Column reflow collects screen and history into one `Vec` and splits it back (change 7 streams it instead). Every container call that differs from upstream carries a `// feathercritty:` comment, so the algorithm text can be diffed against upstream.

### 7. Compact history

`0.26.0+fbterm.5`. The scrollback is stored compactly: every row that scrolls off the screen is encoded once into a byte record, and records are packed into pooled 64 KiB blocks. The visible screen stays a dense ring of `Row`s, exactly as upstream, so the parser's write path is unchanged; history rows are decoded only when something reads them, through the explicit read API of change 6. A full 10,000-line history of short lines takes 0.68 MB instead of about 31 MB. Behavior is unchanged: the differential test compares every cell and query answer with 0.26.0.

**Credit.** The idea of keeping the visible screen dense while storing history rows in a compact form, with pooled buffers and an explicit history read API, comes from Adam Mikołajczyk (Razuer), who proposed it in alacritty/alacritty#9049. feathercritty's implementation is independent and was written from the idea only.

**Format** (`src/grid/compact.rs`, module docs "Record format"; the authoritative description)
- A record is a header (`W` width, `P` cells stored explicitly, `R` runs, `M` marks, `E` extras, as LEB128 varints, plus a bits byte with `WRAPS` and `CLEAR`), the text of cells `0..P` as UTF-8 (one char per cell), the attribute runs (length, fg, bg, flags, extra reference), the marks (column deltas with the structural flags: wide character, spacers, `WRAPLINE`) and the tail cell, which every cell from `P` to `W-1` equals. Trailing blanks and background-colored erased tails cost one tail record.
- Colors are 4 bytes; vte's named colors are written as explicit codes, so a vte renumbering does not change the format.
- `CellExtra` values (zero-width characters, underline color, hyperlinks) stay `Arc`s in one typed queue per history; records refer to them by position, once per run. Records hold no pointers or process-specific values, so blocks could later be written to disk as they are.
- Typical sizes at 126 columns: a short line about 49 bytes, a colored log line about 194 bytes, a dense line about 1.6 KB (0.26.0: 3,024 bytes for every row).

**Store** (`src/grid/history.rs`, module docs "Layout", "Invariants", "Eviction and the pool")
- Records are appended to 64 KiB blocks and never span two; a record above a quarter block gets its own block. Rows are encoded straight into the newest block when it surely has room (`HistoryCell::max_record_bytes`), else through a reused scratch buffer.
- One 16-byte index entry per row. The index grows by doubling up to the limit, so a full history's index holds at most `limit` entries; after a column reflow it can hold up to `limit + lines` (the reflow builds the new history with upstream's `limit + lines` and lowers the limit without shrinking the index).
- Spare blocks: a block whose last row is evicted becomes a spare, and the history keeps **at most 2** (`MAX_SPARES`); new blocks come from the spares first, so steady scrolling with a full history allocates nothing. `clear` and a lower limit (`set_limit`) free what they no longer need and also keep at most 2 spares. The library never calls into the allocator to return memory to the OS; that is the host's decision.
- Block size: 64 KiB. Measured between 16 and 256 KiB in the tuning pass (`benches/RESULTS.md`, "Block size"): larger blocks did not help dense rows, helped short lines at 200x60 only slightly (1.23 to 1.19), cost memory (log lines 2.13 MB at 64 KiB, 2.52 MB at 256 KiB) and moved the zero-allocation steady state further out.

**API** (additions to change 6; existing callers compile unchanged)
- `HistoryCell` (public, `src/grid/compact.rs`; it used to be an empty trait implemented in `src/term/cell.rs`): `type Extra`, `row_wraps`, `encode`, `decode` (returns the bytes consumed), `decode_cell`, and, with defaults, `max_record_bytes` (`None`) and `reflow_info` (`None`). `Grid<T>` requires `T: HistoryCell`; `Cell` implements it in `compact.rs`.
- `RowHeader` appears in the public trait (`encode` returns it) but lives in a private module (it cannot be named outside the crate) and its fields are crate-private: an implementation outside the crate can only return `Default::default()`, not a correct header, so in practice only this crate's cell types implement `HistoryCell`. Treat `RowHeader` as part of the public surface when changing it. `ReflowInfo` (re-exported from `grid`) likewise has crate-private fields and no constructor, deliberately: only the crate's own `Cell` format opts into the reflow byte copy, and an outside implementation keeps the default `reflow_info` (`None`).
- `RowReader` and `GridIterator` decode a history row into their own scratch row once per row (screen rows are lent in place); `Grid::cell` decodes only the cell asked for.
- Cargo feature `test-hooks` (off by default, not a stable API; the crate's own tests enable it through a self dev-dependency): `Grid::new_with_block_size`, `Grid::set_reflow_window` and `Grid::set_reflow_byte_copy`.

**Behavior.** Unchanged against 0.26.0 (with the oracle patches of change 6), with one internal exception that has no visible effect: `Term::clear_line` lowers a row's `occ` after an erase that reaches the end of the line (`Row::set_equal_from`); `Row::reset` then writes the same cells it would have.

**Resize** (`src/grid/resize.rs`, design spec 5.6). The column reflow is upstream's algorithm line for line over two streaming containers: `RowSource` stands for upstream's `take_all()` `Vec` and pops old history rows oldest first, freeing old blocks as it goes; `ReflowSink` stands for upstream's `reversed`/`new_raw` `Vec` (`push`, `last_mut`, `len`, `truncate_newest`, `resize_with_blank`, `finish`), keeps the newest `2 * lines + 2` rows dense and encodes older rows into a new history, decoding rows back when an operation reaches past that window. Peak memory is the old plus the new compact store. History rows the loop would push unchanged but for their width skip the loop and are copied as bytes with only `W` changed (`RowSource::next_reflow`, `Pass::byte_copy_width`). Those conditions are a correct superset of the text of spec 5.6, each refinement taken from upstream's loop: shrinking accepts any empty tail (`GridCell::is_empty`, which is what `Row::shrink` drops), not only the default cell; shrinking without reflow copies too (the loop pushes the cut row either way); and growing uses upstream's whole `should_reflow` (`reflow`, `len < columns`, wrapping last cell), not only "the previous row does not wrap". `byte_copy_width_only_when_the_loop_keeps_the_row`, `reflow_window_one_matches_default` (window 1, byte copy on and off) and the differential test check them.

**Measured results** (Apple M5 Max, release; full tables, method and commands in `benches/RESULTS.md`)
- Memory, history of 10,000 rows at 126x37 (terminal after 12,000 lines minus a new terminal, both crates): short lines 0.68 MB (0.26.0: 30.77 MB), log lines 2.13 MB, wide characters 0.18x, dense cells 0.56x of 0.26.0. Peak during a full-history reflow: 4.75 MB (126->100->126) and 5.57 MB (200->80), against 33.74 and 81.48 MB. Zero allocations per scrolled row once the history is full.
- Reads: regex search over the history 1.32x of 0.26.0 (gate 1.5); `selection_to_string` over 1,000 rows 0.35x (faster: plain rows are read as text); reflow 126->100->126 0.38x, 200->80 1.8x at 7.6 ms (gate "2x or 10 ms"). Lines-only resizes take 2 to 31 microseconds (gate 50 microseconds and 1 ms).
- Large histories: a 100,000-line rewrap takes 3 to 33 ms, 1,000,000 lines about 0.03 to 0.33 s; 1,000,000 short lines take about 58 MB live. On rich content (colors, wide characters, hyperlinks) a 100,000-line rewrap takes 31 to 37 ms against 18 to 26 ms in 0.26.0.
- Ingest against 0.26.0 (three `--gate` sessions): uniform rows 0.96 to 0.98, region scroll 0.99 to 1.00, short lines at 126x37 1.03 to 1.04; alt-screen redraw 0.99 to 1.03; log lines 1.15 to 1.21 and wide characters 1.75 to 1.90 (not gated); the accepted misses below.

**Accepted misses.** Five ingest rows of design spec 6.3 miss their gate, and the gates are unchanged: full-width plain (1.30 to 1.32 against 1.05), dense cells (1.06 to 1.10 against 1.05), typing echo (1.07 to 1.12 against 1.01), short lines at 200x60 (1.17 to 1.18 against 1.10) and alternate-screen redraw (0.99 to 1.03 against 1.01 or the A/A spread). They were accepted on 2026-10-25 and are recorded as measured costs, not loosened. The reason for the first four: each row that scrolls off is read and encoded, while 0.26.0 only rotates its ring, and the encoder has a floor of about 1 ns per stored cell (four field compares per cell, two on `Color`); for a full-width plain row that is about 150 ns against a 5% budget of about 22 ns. Meeting these gates would mean recording runs on the write path (a cost per character in `Term::input`) or `unsafe` SIMD compares, both outside this change's constraints. The 1% rows (alternate-screen redraw, typing echo) are judged at 31 or more interleaved runs with an A/A comparison. The alternate-screen redraw is accepted for a different reason: it does no history work (the alternate screen has no history), and separate processes each holding one crate measured fork and 0.26.0 equal, so the residue (0.99 to 1.03 at 31 runs; 126x37 passed in two of three sessions, 200x60 in one of three) is attributed to the code layout of the combined bench binary; `benches/RESULTS.md`, "Alt-screen redraw", has the figures.

### The differential test's oracle

`tests/differential.rs` compares feathercritty with 0.26.0 on generated byte streams. Since `0.26.0+fbterm.4` the comparison crate is the vendored, patched 0.26.0 source in `tests/oracle/`, a path dev-dependency named `alacritty_terminal`, instead of the crates.io release:
- The oracle is the published 0.26.0 `src/`, `Cargo.toml` and `LICENSE-APACHE` plus exactly the patches listed in `tests/oracle/PATCHES.md` (the `occ` fix and the "no row" reads of change 6; changes 1 and 5 are modeled by the harness, not patched).
- `tests/oracle_pristine.rs` checks it offline: it applies `PATCHES.diff` in reverse and compares SHA-256 values with `MANIFEST`, so the vendored files are provably 0.26.0 plus the patches.
- Vendored files are exempt from the fork notice line (unmodified ones are byte-identical to upstream; patched ones carry a "Patched by the featherbit authors" line). `PATCHES.diff` and `MANIFEST` are data and carry none.
- To move the oracle to a new upstream release, follow "Moving to a new upstream release" in `tests/oracle/PATCHES.md` and "Moving the oracle to a newer upstream release" in `tests/support/mod.rs`.

## Updating from upstream

The `upstream` branch and the release base are produced with `git subtree split`, which is deterministic: the same upstream commits always give the same split commits (author and committer data are copied from the originals), so a later split of newer upstream history extends the existing `upstream` branch and shares its commits. The current split was made with git 2.54.0 from upstream `master` at `542147067dd016fc5f49120ef0ba605a98a4e3a7` (split tip `17d568a11bc2161304a0e12d321d1e54f5d5afe6`).

1. Split the upstream history (from a fresh or updated clone; only reading from upstream):

   ```sh
   git clone https://github.com/alacritty/alacritty.git
   cd alacritty
   git subtree split --prefix=alacritty_terminal origin/master
   # For a release, split its tag too (release commits usually live on a release branch):
   git subtree split --prefix=alacritty_terminal alacritty_terminal_vX.Y.Z
   ```

   Each command prints the tip of the split history.

2. Bring it into feathercritty and fast-forward `upstream` (the update must be a fast-forward; if it is not, the split was not reproduced, so check the git version and the command):

   ```sh
   cd ../feathercritty
   git fetch ../alacritty <master split sha>:refs/heads/upstream
   git fetch ../alacritty <release split sha> && git tag alacritty_terminal_vX.Y.Z <release split sha>
   git push origin upstream alacritty_terminal_vX.Y.Z
   ```

3. Adopt upstream changes on `main` by merging, never by rebasing: featherbit terminal pins commits of `main`, and they must stay reachable.

   - A single upstream fix: `git cherry-pick -x <sha from upstream>`.
   - A new release: `git merge alacritty_terminal_vX.Y.Z`, resolve conflicts (usually `Cargo.toml` and `Cargo.lock`), drop changes that upstream now carries, set the version to `X.Y.Z+fbterm.1`, re-vendor the oracle, and update the change list above.

4. Run the checks under [Development](#development), push `main`, and bump the `rev` in featherbit terminal.
