# feathercritty

feathercritty is the terminal emulation library used by [featherbit terminal](https://github.com/featherbitplatform/terminal): the VT parser handler, the grid with its scrollback, selection, search and the PTY event loop. It is a fork of `alacritty_terminal` 0.26.0 with a few small changes, listed below.

The crate is not published on crates.io. Use it as a git dependency pinned to a commit:

```toml
[dependencies]
feathercritty = { git = "https://github.com/featherbitplatform/feathercritty", rev = "<full commit sha>" }
```

## Origin

The repository holds the history of the `alacritty_terminal/` directory of [alacritty/alacritty](https://github.com/alacritty/alacritty), extracted with `git subtree split` (see [Updating from upstream](#updating-from-upstream)):

- `upstream` is the extracted history of upstream `master`, unchanged.
- `main` starts at the `alacritty_terminal_v0.26.0` release (tag `alacritty_terminal_v0.26.0` here, commit `a6b23e80c7fe4e416e96a39b34cb300fa9db3aca`; the release commit lives on upstream's `v0.17` branch, so it is not on `upstream`) and adds the changes below as separate commits.

## Why this fork exists

feathercritty is a fork of [`alacritty_terminal`](https://github.com/alacritty/alacritty/tree/master/alacritty_terminal), the terminal emulation library of the Alacritty project, maintained for [featherbit terminal](https://github.com/featherbitplatform/terminal).

featherbit terminal is developed with the help of AI coding tools. The Alacritty project does not accept contributions that include content generated by large language models ([CONTRIBUTING.md](https://github.com/alacritty/alacritty/blob/master/CONTRIBUTING.md)), and we respect that choice. Rather than send such changes upstream, we keep them here, so featherbit terminal can keep moving forward (for example on scrollback memory use) without asking the Alacritty maintainers to review or carry them.

This fork is not affiliated with or endorsed by the Alacritty project. Please do not report issues with this fork to Alacritty; open them here instead. All credit for the original work goes to the Alacritty authors.

## Changes from alacritty_terminal 0.26.0

Files changed by this fork start with the line `// Modified by the featherbit authors for feathercritty; see README.md for the list of changes.` (`#` in `Cargo.toml`).

### 1. Keyboard mode stack eviction (crash fix, upstream commit)

`src/term/mod.rs`, `Term::push_keyboard_mode`. When the kitty keyboard protocol's flag stack is full (`KEYBOARD_MODE_STACK_MAX_DEPTH`, 4096), 0.26.0 evicts the oldest entry from the wrong stack:

```rust
// before
let removed = self.title_stack.remove(0);
// after
let removed = self.keyboard_mode_stack.remove(0);
```

With an empty title stack the original line panics (`Vec::remove(0)` on an empty vector), so any program or remote host that sends `CSI > flags u` 4097 times crashes the terminal's parser while the protocol is enabled. This is upstream's own fix ("Fix Kitty keyboard mode stack size limit", made after 0.26.0), cherry-picked from `upstream` with its original authorship.

### 2. Scroll counter on the grid (scrollback search)

`src/grid/mod.rs`: `Grid` gains a `scrolled_lines: i64` field (skipped by serde), incremented by `positions` where `Grid::scroll_up` rotates the whole buffer into history, and a getter `Grid::scrolled_lines()`. `src/grid/resize.rs`: `grow_lines` subtracts the lines it adds (lines pulled back from history move down the screen, and the rotation its `scroll_up` counts only undoes the growth), so the counter can go below zero (wrapping arithmetic). `scrolled_lines() + line` is a line number that stays the same while output scrolls the line upward and while the screen grows or shrinks, which featherbit terminal's find bar uses to keep its matches and current match in place as new output arrives. Nothing in the library reads the field.

### 3. Inactive grid getter (tab export)

`src/term/mod.rs`: `Term::inactive_grid()` returns the grid that is not shown (the normal screen and its scrollback while the alternate screen is active). featherbit terminal's tab export writes the normal screen's history even while a full-screen program (vim, less, top) has the alternate screen up. Read-only; nothing else changes.

### 4. Packaging

- The package is named `feathercritty`; the doc test and `tests/ref.rs` use the new name. Authors and license are unchanged; `repository` and `homepage` point here, and `publish = false` keeps the crate off crates.io.
- Version scheme: `<alacritty_terminal version>+fbterm.<n>`, currently `0.26.0+fbterm.4`. The build metadata (`+fbterm.n`) counts this fork's revisions on top of one upstream release and starts again at 1 when `main` moves to a new upstream release. Cargo ignores build metadata when comparing versions, which does not matter for a git dependency pinned by `rev`.
- The manifest no longer inherits `edition` and `rust-version` from the Alacritty workspace (both set to the workspace's values, 2024 and 1.85.0), and `readme` points to this file.
- `LICENSE-APACHE` is a copy of the upstream file instead of a symlink into the Alacritty workspace. The Alacritty workspace's `rustfmt.toml` (nightly options) and the `Cargo.lock` shipped with the published 0.26.0 crate are included so the crate formats and builds on its own.
- `src/lib.rs` allows `clippy::question_mark`: clippy releases newer than the upstream code flag three matches in `src/tty/unix.rs`, and the crate denies `clippy::all`. Allowing the lint keeps the upstream code unchanged.
- The reference test data in `tests/ref` (about 46 MB on disk) is kept. The whole repository history packs to about 1 MiB, so fetching it as a git dependency stays cheap.

### 5. Regex search over wrapped wide characters (hang fix)

`src/term/search.rs`: `Term::regex_search_internal`, `Term::regex_search_left`, `Term::regex_search_right`, `RegexIter::next`, `RegexIter::skip`, and new helpers `Term::skips_over`, `Term::search_distance`, `Term::glyph_end`, `Term::matches_overlap` and `Term::stale_spacer_end`. `0.26.0+fbterm.2` fixed the wrapped wide character cases; `0.26.0+fbterm.3` completed the change. It added hard bounds, handled stale leading spacers, and limited matches to the range.

The trigger is a leading spacer.
- With a wrapped wide character after it (the wide character at column 0 of the next line, its spacer at column 1), searches step over the character two or three cells at a time: left from its spacer to the leading spacer, right from the leading spacer to its spacer. 0.26.0 only checks for the search's end on the cells where a step lands.
- With a stale leading spacer, one whose next line does not start with a wide character (a resize or an erase leaves it behind, sometimes in the middle of a line), a rightward step still reads the next cell in its place and steps over the cell after it. The search lands one cell further than it read, and a match can end behind its own search origin.

- Before:
  - A search whose end was a cell inside such a step was never stopped there. `regex_search_internal` wrapped around the buffer and either looped forever or returned a match from beyond the end. This applied to a leftward `search_next` with `max_lines`, which puts its end at column 0 of an arbitrary line. It also applied to the empty pattern.
  - `RegexIter` stopped only when a match ended exactly on its end. A match covering the end, or ending behind its origin next to a stale spacer, sent the next search around the buffer, and the iterator cycled through its matches forever. This hung unbounded `search_next` calls too, the find bar's ordinary case.
  - Matches could lie outside the searched range. A rightward search limited to a line ending in a leading spacer returned a match from the next line: the last search of every `RegexIter` goes from the end to itself, and from a leading spacer it skips onto the next line and reads on. A stale spacer at either end of a range let a match end on the next line.
- After:
  - **Exact stops.** `skips_over` checks the cells a step jumps over. `regex_search_internal` stops when a step jumps over its end, including the first step from `start`, and `RegexIter::skip` stops when the new origin jumps over the end. Going right, `RegexIter::next` also stops when the match ends on the last cell of the end's character (`expand_wide`), unless the search started inside that character after the end.
  - **Hard bounds, so no grid state can make them loop.**
    - `regex_search_internal` counts its steps and stops once it has taken as many as there are cells from `start` to `end` (`search_distance`). Every step advances at least one cell. A search from a cell to itself gets one full lap, as far as 0.26.0 goes.
    - An unbounded search's range is the whole buffer less one cell, so it wraps at most once.
    - `RegexIter` requires every new origin to lie further from its start than the previous one. A match that ends past its own origin (next to a stale spacer) would put the next origin behind the last one; the next search then starts one cell past the farther of the last origin and that match's far end instead, so later matches in the range are still found. Iteration stops once an origin would pass the end, so it runs at most once per cell of its range.
    - `RegexIter::next` skips a match equal to the first or the last match it returned. The last search of a range that wraps around the whole buffer can find the first match again. It also skips a match overlapping the last one when its search started from an origin the rule above moved forward. Matches are therefore never repeated. Other overlaps are 0.26.0's and stay: going left, each search starts one cell left of the previous match's right end, inside that match, so consecutive leftward matches can overlap. Going right they never do.
  - **Matches stay in their range.**
    - **Glyph completion, kept from 0.26.0.** The character at a range's end is read whole. Right onto a leading spacer reads the wrapped wide character, and the match ends on its spacer on the next line. Left onto a wrapped wide character reports it at its leading spacer.
    - **`regex_search_right` and `regex_search_left`.** They return no match whose far end lies beyond that completion; `regex_search_right` also returns none that starts beyond the range. When the end is a stale leading spacer, `regex_search_right` reports a match ending on its completion cell as ending at the spacer itself (`stale_spacer_end`). The second search, back to `start`, may still complete the character at `start`, up to two cells past it, as 0.26.0 does.
    - **Leftward `RegexIter::next`.** It cuts a match whose right end lies beyond the start of a bounded range back to that start. A match that cannot be cut without turning it around ends the iteration.
    - **Text and decisions.** Both searches always read the text as 0.26.0 does, so whether there is a match stays 0.26.0's; only where it is reported changes, and only for matches 0.26.0 would have returned outside the range.
  - **Unchanged results.** Where 0.26.0 terminates with matches inside the range, it runs the same code and gives the same results; the bounds and checks are not reached there. The differential test against 0.26.0 (`tests/differential.rs`, with the oracle described under Development) checks this.
- Tests: `wrapped_wide_*`, `stale_leading_spacer_*`, `stale_spacer_*`, `range_ending_on_*` and `empty_pattern_terminates`. They run with a timeout, so a regression fails instead of hanging. They include the grids from the differential soak and an exhaustive run over 2- to 4-column grids with wrapped and stale leading spacers, with and without scrollback. The exhaustive run also checks that every match lies in its range (allowing only the glyph completion at each end) and that `RegexIter` never repeats a match, and going right never returns one overlapping the previous one.
- When merging upstream: re-run those tests with this change removed. If upstream fixed the end-cell skip, bounds the loops itself and keeps matches in range, and they pass, drop this change and its helpers. If `skip_fullwidth`, `expand_wide` or `RegexIter` changed, check that the `// feathercritty:` comments still describe the code. Keep the hard bounds unless upstream has its own.
- Not changed:
  - On 2-column grids, the right step from column 0 over a leading spacer to column 1 also looks like a line break to `regex_search_internal`'s line-break check, which resets the match. This is 0.26.0 behavior, and it does not hang.
  - A stale leading spacer is read as 0.26.0 reads it. Going right, the search reads the next cell in its place and skips the cell after that; going left, it reads a blank.
  - Going right past a stale leading spacer, the two searches can disagree. The first one reads the next line's first cell in place of the spacer; the second one, reading back from where the first one stopped, reads the cell after it. The match then fails and the iteration ends there, so later matches in the range are not returned. This is 0.26.0 behavior.

### 6. Screen and history split (explicit history reads)

`0.26.0+fbterm.4`. Phase 1 of the compact scrollback work: the grid keeps the visible screen and the scrollback in two containers, and every read of scrollback goes through an explicit API. The scrollback is still dense (a `VecDeque` of `Row`s) in this release, so memory use and speed are about what 0.26.0 had (ingest within about 4%, see the benchmark note below); the point is the API, which lets a later release store history compactly without changing callers.

**API**
- `Grid<T>` is `{ screen: Screen<T>, history: History<T> }`. `Grid::screen()` and `Grid::screen_mut()` return the screen, a handle over upstream's `Storage` ring that implements `Index`/`IndexMut` for `Line` and `Point` with upstream's `debug_assert!` range checks. The `max_scroll_limit` field is now `history.limit()`.
- **`Grid` itself no longer implements `Index`/`IndexMut`.** Indexing is screen-only (`grid.screen()[line]`, lines `0..screen_lines`). History lines (negative `Line`) are read through:
  - `RowReader<T>`: `RowReader::new()` and `reader.row(&grid, line) -> &Row<T>` for a whole row of screen or history. Keep one reader and reuse it; a later release decodes history rows into its scratch row.
  - `Grid::cell(point) -> T` (an owned cell), `Grid::wraps(line) -> bool` and `Grid::is_clear(line) -> bool`, for single reads that work for screen and history lines.
- `GridIterator` yields `Indexed<T>` by value (it used to borrow `&T` from the grid). `GridIterator::cell(&self) -> &T` borrows the current cell without cloning; `advance`/`retreat` (`pub(crate)`) step without producing an item.
- `History<T>` (`src/grid/history.rs`, new) owns the scrollback: `new`, `len`, `is_empty`, `limit`, `set_limit`, `push_newest(&Row)`, `pop_newest`, `pop_oldest`, `read`, `update`, `wraps`, `is_clear`, `clear`. Cells stored in it implement `HistoryCell` (since phase 2 in `src/grid/compact.rs`, with the row codec).
- The only write to history outside scrolling and resizing is the one in `Term::input` (`Grid::update_history_row`).
- (Phase 1 only: `History::push_newest_recycle` swapped the departing screen row for a recycled one in `scroll_up`. Phase 2, below, replaced it with `push_newest` plus the in-place reset upstream does.)
- serde form is unchanged: the same fields as upstream (`raw.inner` from the bottom line up, `zero` 0, `len`, `visible_lines`, the scroll limit), through private proxy structs. Deserialization splits at the grid's `lines`, because old reference files carry a stale `visible_lines`. `tests/ref/` data is unchanged.

**Merging a new upstream release.** Upstream code that indexes the grid (`self.grid[point]`, `grid[line]`, `grid.raw`-style access) will not compile after a merge. Classify each site:
- *Screen*: the line is always `0..screen_lines` (handler writes, cursor, the visible region). Use `grid.screen()` / `grid.screen_mut()`.
- *History-capable*: the line can be negative (selection text, search, vi motions, anything that follows a point or a neighbouring line). Use `Grid::cell`, `Grid::wraps`, `Grid::is_clear`, a `RowReader`, or `GridIterator`.

The sites classified as history-capable in 0.26.0: `Term::line_to_string`, `Term::expand_wide`, the vi cursor in `RenderableCursor`, in `search.rs` `regex_search_internal`, `glyph_end`, `stale_spacer_end`, `skip_fullwidth`, `bracket_search`, `inline_search_right`, `line_search_left`/`line_search_right`, in `vi_mode.rs` `ParagraphUp`/`ParagraphDown` and `semantic` (`expand_semantic`, `is_space`, `is_wrap`), and every `GridIterator` user (`display_iter`, `clear_viewport`, the regex, bracket, semantic and inline searches). Everything else is screen.

**Behavior changes made with it** (both are also patched into the differential test's oracle, see Development)
1. *`Row` `occ` invariant* (`src/grid/row.rs`, `Row::grow` and `Row::append`). Upstream documents that all cells after `occ` are equal, and `Row::reset` relies on it, but `grow` padded with default cells without raising `occ`, and `append` did `occ += n` even when `occ` was below the old length. A reset could then leave stale cells behind, and what a recycled row looked like depended on which physical row the ring had recycled.
   - Before: `grow` left `occ` alone; `append` set `occ += vec.len()`.
   - After: `grow` first sets `occ = max(occ, len)`; `append` sets `occ = len + vec.len()` when `vec` is not empty.
2. *Reads outside the grid are "no row"*. 0.26.0 read lines just outside `topmost_line()..=bottommost_line()` in a few places: debug builds failed a `debug_assert!`, release builds read whichever row the ring held there (a cache row or a wrapped-around screen row).
   - `Term::line_to_string`. Before: a selected line ending in a leading wide-char spacer appended `grid[line - 1][Column(0)].c`, even on the topmost line. After: it adds nothing above the topmost line.
   - Vi motions. Before: the cursor could leave the grid (`Middle` on a one-line screen without history, `Right`/`Last` across a wrap or leading spacer on the bottom line). After: `ViModeCursor::motion` clamps the point into the grid (`grid_clamp(term, Boundary::Grid)`).
   - Iterators and readers. Before: undefined (see above). After: `Grid::cell` and `GridIterator::cell` return a default cell, `Grid::wraps` returns false, `Grid::is_clear` returns true. `RowReader::row` and the `History` methods keep a `debug_assert!` (a caller bug) and in release return default cells of the grid's width, a no-op, false and true.

**Other changes**
- `Storage::initialize` grows by exactly the rows needed (upstream added at least 1000 at a time, a history cache); it keeps upstream's hidden rows beyond `len`, which `scroll_up` recycles. (Phase 1 also had a small spare-row pool there; phase 2 removed it, the history's block pool does that job.)
- `Grid` equality compares content, including history.
- `Grid::scroll_up` moves the departing rows into history, then rotates and resets as upstream did.
- `resize.rs`: `grow_lines` moves popped history rows onto the new top rows and removes only the rows `scroll_up` pushed; it clamps the display offset unconditionally (upstream's `decrease_scroll_limit` always clamped). Column reflow collects screen and history into one `Vec` and splits it back (phase 2 streams it instead, below). Every container call that differs from upstream carries a `// feathercritty:` comment, so the algorithm text can be diffed against upstream.

**Changed upstream files, and what to watch when merging**
- `src/grid/mod.rs`: `Grid` fields, `Index`/`IndexMut` removed, `scroll_up`/`scroll_down`/`clear_viewport`/`reset`/`update_history`/`clear_history`/`initialize_all`, `GridIterator`, serde, `PartialEq`. Re-read every upstream change to these and to anything that touched `raw` or `max_scroll_limit`; classify new grid reads as screen or history.
- `src/grid/resize.rs`: `grow_lines`, `shrink_lines`, the reflow container calls. Diff the algorithm against upstream; only the marked container calls differ.
- `src/grid/row.rs`: `grow`, `append`, manual `Default` (no `T: Default` bound) and `Clone` (allocation-reusing `clone_from`). Check new `Row` mutators keep the `occ` invariant.
- `src/grid/storage.rs`: `initialize`, spare pool, `from_rows`, struct literals gained `spare`. Check changes to the hidden-row recycling.
- `src/grid/tests.rs`: tests rewritten for the split (list below). Keep upstream's new tests if they only touch the screen; port the others to `screen()` or `History`.
- `src/term/mod.rs`: handler writes through `screen_mut()`, `line_to_string` (shared `RowReader`, topmost guard), `expand_wide`, `RenderableCursor`, `Term::input`'s history write, `mock_term`. New code that indexes the grid must be classified.
- `src/term/search.rs`: grid access only (plus the change-5 logic): iterator stepping, `Grid::wraps`/`cell`. Check that the `// feathercritty:` comments still describe the code.
- `src/term/cell.rs`: `impl HistoryCell for Cell`. If `Cell` gains a field, keep `row_wraps` in step.
- `src/vi_mode.rs`: `Grid::cell`/`is_clear` reads, the motion clamp. New motions that look at neighbouring lines need a classification.
- `tests/ref.rs`: the failure printout reads through `RowReader`.
- New: `src/grid/history.rs`, `tests/oracle/`, `tests/oracle_pristine.rs`, `tests/support/`, `tests/differential.rs`, `benches/`, `examples/memory.rs`.

**Replaced tests** (old to new)
- `storage.rs`: `grow_after_zero` to `grow_after_zero_adds_exact_rows`; `grow_before_zero` to `grow_before_zero_adds_exact_rows`; `initialize` to `initialize_adds_exact_rows`. The other storage tests are upstream's; only their struct literals gained `spare`.
- `grid/tests.rs`: `scroll_down_with_history` pushes with `history.push_newest` instead of the removed `increase_scroll_limit`; `test_iter` uses owned items.
- New tests cover the split (`scroll_up_*`, `grow_lines_*`, `shrink_lines_*`, `row_reader_and_cell_read_screen_and_history`, `reads_outside_the_grid_are_no_row`, `iterator_*`, `serde_keeps_upstream_format`, and others) and the `occ` fix (`grow_raises_occ_to_old_len`, `append_keeps_occ_invariant`).

**Phase 2 (unreleased, on `feature/compact-history`): compact rows in pooled blocks.** History rows are stored as compact byte records (`src/grid/compact.rs`) in pooled byte blocks (`src/grid/history.rs`; the module docs describe the layout, invariants, eviction and the pool). The `History` API is unchanged; `RowReader` and `GridIterator` decode a history row into their own scratch row once per row (screen rows are still lent in place), `Grid::cell` decodes only the cell asked for (`HistoryCell::decode_cell`). `Grid<T>` now requires `T: HistoryCell`. The `test-hooks` cargo feature (off by default; the crate's own tests enable it through a self dev-dependency) exposes `Grid::new_with_block_size` and `Grid::set_reflow_window`, which `tests/alloc.rs` (steady scrolling allocates nothing; reflow peak) and the differential test's `DIFF_TINY=1` (256-byte blocks, reflow window 1) use. Files changed by phase 2, and what to watch when merging:
- `src/grid/mod.rs`: `scroll_up` encodes the departing rows (`push_newest`) and resets the recycled rows in place, as upstream; `Grid` impls gained `T: HistoryCell`; `GridIterator` keeps a scratch row; equality and serde decode history. Re-check a changed `scroll_up` rotation against the pushes.
- `src/grid/resize.rs`: `grow_lines` decodes popped history rows straight into the screen rows. The column reflow streams (design spec 5.6): `RowSource` stands for upstream's `take_all()` `Vec` and pops the old history's rows one at a time, oldest first (old blocks are freed as the pass goes); `ReflowSink` stands for upstream's `reversed`/`new_raw` `Vec` with exactly the operations upstream used (`push`, `last_mut`, `len`, `truncate_newest`, `resize_with_blank`, `finish` for the final reverse, trim and split), keeps the newest `2 * lines + 2` rows dense and encodes older rows into a new history. Rows reached past the window are decoded back, so the result does not depend on the window (`Grid::set_reflow_window` under `test-hooks`; `DIFF_TINY=1` sets it to 1). Peak during a full-history reflow is about the old plus the new compact store. When merging: diff `grow_columns`/`shrink_columns` against upstream (only the `// feathercritty:` container calls differ); a new `Vec` operation upstream uses on these containers must be added to the sink with the same meaning.
- `src/grid/storage.rs`: the phase-1 spare-row pool is gone (closer to upstream again); `replace_inner` is removed (the reflow builds the screen ring with `from_rows`, now not serde-only).
- `src/grid/compact.rs`: `HistoryCell::decode` returns the bytes consumed; `decode_cell` reads one cell.
- `Cargo.toml`: `test-hooks` feature and the self dev-dependency.

**Benchmarks.** `cargo bench` (`benches/`, `benches/BASELINE.md`) compares against the oracle. The spec gate for resizing the screen by lines only is absolute, not a ratio: at most 50 microseconds per step of up to 10 lines and 1 ms per 37 to 1 to 37 pair, with a full 10,000-line history. Upstream does O(1) counter updates there; the fork moves the rows between the two containers (about 0.08 microseconds per small step), so the old ratio row (about 1.9) is informational only.

### The differential test's oracle

`tests/differential.rs` compares feathercritty with 0.26.0 on generated byte streams. Since `0.26.0+fbterm.4` the comparison crate is the vendored, patched 0.26.0 source in `tests/oracle/`, a path dev-dependency named `alacritty_terminal`, instead of the crates.io release:
- The oracle is the published 0.26.0 `src/`, `Cargo.toml` and `LICENSE-APACHE` plus exactly the patches listed in `tests/oracle/PATCHES.md` (the `occ` fix and the "no row" reads of change 6; changes 1 and 5 are modeled by the harness, not patched).
- `tests/oracle_pristine.rs` checks it offline: it applies `PATCHES.diff` in reverse and compares SHA-256 values with `MANIFEST`, so the vendored files are provably 0.26.0 plus the patches.
- Vendored files are exempt from the fork notice line (unmodified ones are byte-identical to upstream; patched ones carry a "Patched by the featherbit authors" line). `PATCHES.diff` and `MANIFEST` are data and carry none.
- To move the oracle to a new upstream release, follow "Moving to a new upstream release" in `tests/oracle/PATCHES.md` and "Moving the oracle to a newer upstream release" in `tests/support/mod.rs`.

## Updating from upstream

The `upstream` branch and the release base are produced with `git subtree split`, which is deterministic: the same upstream commits always give the same split commits (author and committer data are copied from the originals), so a later split of newer upstream history extends the existing `upstream` branch and shares its commits. The current split was made with git 2.54.0 from upstream `master` at `542147067dd016fc5f49120ef0ba605a98a4e3a7` (split tip `17d568a11bc2161304a0e12d321d1e54f5d5afe6`).

1. Split the upstream history (from a fresh or updated clone; only reading from upstream):

   ```sh
   git clone https://github.com/alacritty/alacritty.git
   cd alacritty
   git subtree split --prefix=alacritty_terminal origin/master
   # For a release, split its tag too (release commits usually live on a release branch):
   git subtree split --prefix=alacritty_terminal alacritty_terminal_vX.Y.Z
   ```

   Each command prints the tip of the split history.

2. Bring it into feathercritty and fast-forward `upstream` (the update must be a fast-forward; if it is not, the split was not reproduced, so check the git version and the command):

   ```sh
   cd ../feathercritty
   git fetch ../alacritty <master split sha>:refs/heads/upstream
   git fetch ../alacritty <release split sha> && git tag alacritty_terminal_vX.Y.Z <release split sha>
   git push origin upstream alacritty_terminal_vX.Y.Z
   ```

3. Adopt upstream changes on `main` by merging, never by rebasing: featherbit terminal pins commits of `main`, and they must stay reachable.

   - A single upstream fix: `git cherry-pick -x <sha from upstream>`.
   - A new release: `git merge alacritty_terminal_vX.Y.Z`, resolve conflicts (usually `Cargo.toml` and `Cargo.lock`), drop changes that upstream now carries, set the version to `X.Y.Z+fbterm.1`, re-vendor the oracle, and update the change list above.

4. Run the checks under [Development](#development), push `main`, and bump the `rev` in featherbit terminal.
